# V6 规划探针：MoveCube「继续往外推」与 3 个更难档参数（2026-09-25，只读调查）

> 仓库 `newtaskRelease-v5`，HEAD `da77662`。未改任何被 git 跟踪的文件；本目录全部为本机留档、不进 git。
> 用户原话（V6）：「把 movecube 继续往外推」；V6 另要给**有梯度的任务**加 3 档比 xhard 更难的档（原三档逐位冻结，V1 闸门）。

## 〇、结论先行

1. **现框下 R 的物理上限是 0.0849 m，实用上限约 0.07 m。** 执行段 goal 中心只在 `[-0.06, 0.06]²` 里抽（`goal_execution.region_half_size 0.1` − 圆盘半径 0.04），角点离圆心 `0.06·√2 = 0.0849`。R=0.07 时执行段 goal 每次抽样被拒 93.3%，256 次预算下耗尽概率 2.1e-8，布局成功 5000/5000；R=0.08 时耗尽概率 17.7%（实测 341/2000 局失败）；R≥0.0849 必然全部失败。而且 R=0.07 时执行段 goal 只剩 4 个角上很小的弧形片（半径全在 [0.07, 0.085]），多样性很差。**所以要推到 R≥0.08，必须放大采样框。**
2. **原版 MoveCube 没有难度梯度**：`config_easy/medium/hard` 都指向同一个 `config_native`，`NATIVE_SAMPLING` 也不区分档位（源码注释：「本环境原本没有难度分档，现有全局常量即 hard；三档同值」）。**按用户「给有梯度的任务加 3 档」的口径，MoveCube 可能不在加 3 档的范围内**；它在 V6 的必做项可能只有「把 xhard 往外推」。下面仍给出如果要加 3 档的梯度方案。
3. **推荐做法：环带 + 放大框 + 远端封顶 + 杆避让**，即方案 (b)+(c)+(d) 组合：
   - goal、方块候选、方块最终都只许落在环带 `R_in ≤ |c| ≤ R_out` 里（杆仍只查内半径）；
   - 各采样框半宽放大到 `R_out`，让环带能完整放进框里；
   - 中心 x 不超过 0.11（**+x 远离机器人的一侧不外扩**，可达性代理维持在 V5 水平）；
   - 方块中心到杆身线段 ≥ 0.04（候选处再加 0.02 余量）：顺带修掉 V5 已有的「方块生成时压在杆上」问题（V5 每段 2.7%，放大框后会升到 4～6%）。
   三档 `[R_in, R_out]` 取 `[0.08,0.12] / [0.10,0.14] / [0.12,0.16]`：离线各跑 20000 局，布局成功都是 20000/20000，front 相机无出画，可达性代理与 V5 持平。
4. **演示长度与成功判据基本不受影响。** 方块到 goal 的距离均值从 V5 的 0.156/0.136（演示段/执行段）升到 0.166、0.189、0.212（三档）。v5-01 三局总帧数是 481/281/280，V5 S3c 13 局最长 685 步，都远低于 `fail_safe_limit = 5000`。判据 `is_obj_pushed_onto`（0.048）与 `is_obj_dropped_onto`（0.05）都是按水平距离算的定值，跟位置无关。**真正要实测的风险是规划器在更外圈能不能成功**（peg_push 的 PlannerExhausted、推偏），离线副本量不到，必须在模拟器里做演示 smoke。

## 一、现状：V5 xhard 的采样逻辑（锚点：`MoveCube._load_scene`）

| 物体 | 采样框（中心） | 禁区判据 | 预算 | 备注 |
|---|---|---|---|---|
| 杆（演示/执行各一根） | 根 = `(x_jitter, ±0.2 + y_jitter)`，抖动 ±0.05（`peg_position_policy.jitter_span 0.1`）；yaw ±π（`peg_yaw_range.xhard`） | 杆身轴线段 `root + t·u`，`t∈[−0.15, +0.05]`（`_peg_axis_extent`，可视外形）离 (0,0) 的最近点 `< R` 就把 x、y、yaw 三个一起重抽（`_xhard_sample_peg_outside_zone`；`base_y` 不重抽） | 128（`center_exclusion.max_trials`），耗尽抛 `SceneGenerationError` | 建好杆后由 `_xhard_verify_peg_extent` 按实际几何复核 |
| 演示段 goal（`goal_site`） | `spawn_random_target`，`region_half_size 0.15`、半径 `0.02×2 = 0.04` ⇒ 中心落在 **[−0.11, 0.11]²** | 中心 `< R` 就拒（`center_exclusion`） | 256（`spawn_random_target` 默认值） | 没有任何障碍物（`avoid=None`、`include_existing=False`） |
| 执行段 goal（`goal_site_2`） | `region_half_size 0.1` ⇒ 中心落在 **[−0.06, 0.06]²** | 同上 | 256 | **这是限制 R 的瓶颈** |
| 方块候选（局部函数 `_sample_cube_center`，两段各一次） | `center_span 0.2`、`center_offset −0.1` ⇒ [−0.10, 0.10]² | `|c−g| > 5×0.02 = 0.10`，且中心 `≥ R`，两条共用同一次试验 | 128（`cube_rejection.max_trials`） | 候选不写进规格 |
| 方块最终（`spawn_random_cube`） | 以候选为中心 `region_half_size 0.05 − half 0.02` ⇒ 候选 ±0.03 | 中心 `< R` 就拒；xhard 传 `include_existing=False` | 256 | **不再查与 goal 的距离、也不查与杆的距离** |

- 禁区：`config_xhard.center_exclusion = {shape: circle, center: [0,0], radius_m: 0.05, judge: object_center, max_trials: 128}`，由 `_native_decision` 分别放进 `demo_layout.xhard` 和 `execution_layout.xhard` 两份（两段各自消费），`_xhard_center_exclusion` 负责校验。
- **演示段和执行段的区别**：两段的杆、goal、方块各抽一套。执行段 goal 的框更小（半宽 0.06 对演示段 0.11），这是原版（`NATIVE_SAMPLING.positions.goal_execution`）就有的设定。执行段的 `cube_2`/`goal_site_2` 只用来取位姿，`_initialize_episode` 会把它们传送到 (10,±10,1)，阶段切换时再把 `self.cube` 挪到 `cube_init_pose_2`。
- 调用顺序：length/radius → 演示段 base_y 与杆循环 → 执行段 base_y 与杆循环 → obj_sample、dir_sample → 两段 goal → 演示段候选与方块 → 执行段候选与方块 → 两次 `way_idx`。

## 二、离线副本与校核

- `mc_v6.py`：逐次调用 torch 的副本，调用顺序和判据与 `_load_scene` 的 V5 xhard 分支相同，并做了参数化（`R`、`R_out`、`gd_half`、`ge_half`、`cand_half`、`min_cg`、`peg_gap`、`x_cap`、各预算）。**默认参数下与 `scripts/configs/newtask-v5/v5-01/specs.jsonl` 的 MoveCube 10 行逐值一致**（`VALIDATE_V5 10/10`，比对了杆偏移/yaw/重抽次数、goal、方块 xy 与 yaw、两次 way_idx）。
- `geom.py`：解析接受率（格点积分）；front 相机投影（`MoveCube._default_sensor_configs` 实际用的 `base_camera`：eye (0.3,0,0.4)、target (0,0,−0.2)、fov π/2、256²，也就是 h5 里的 `front_rgb`）；桌面边界；可达性代理（按 `solve_push_to_target_with_peg`/`solve_push_to_target` 的公式算路点，量到基座 (−0.615,0) 的水平距离）；杆与方块的 OBB 重叠。
- `sweep_v6.py`：分四组扫描，`frozen`（V5 框、只加大 R）、`grid`（框 × R）、`final`/`ring`（候选三档，带热图）、`variants`（x_cap、peg_gap、min_cg、环带的逐项对照）。输出在 `frozen.out`、`grid.out`、`final.out`、`ring.out`、`variants.out`。
- `budget_tail.py`：按每局已接受的 goal 和杆，算方块候选的条件接受率，得到 128 次预算下的**期望耗尽概率和最坏局**（输出 `budget_tail.out`）。
- `h5_frames.py`：统计 v5-01 三局 h5 的帧数。

## 四、放大框需要核对的边界

- **桌面**（`TableSceneBuilder.build` 的 aabb）：x ∈ [−0.740, 0.469]，y ∈ [−1.215, 1.203]。所有候选都在桌面内，不构成约束。
- **front 相机**：在桌面上的可见范围是：沿 y=0 时 x ∈ [−0.90, 0.43]；y 半宽在 x=0 处为 0.49、x=0.2 处为 0.40、x=0.4 处为 0.31。所有方案三物体出画都是 0.00%，最小像素余量 p1 约 17.5 px（最小值 10.5 px 来自杆，与 R 无关）。**相机不构成约束，除非 +x 推到 0.35 以外。**
- **机械臂可达**（基座 (−0.615, 0)，Panda 名义臂展约 0.855 m）：这是 **+x 方向**的主要风险。代理量取 peg_push 两个路点（起点 `cube−0.1d−0.1·lat·dir`、终点 `goal−0.03d−0.1·lat·dir`）中离基座较远的那个。V5 下 >0.80 占 3.6%，p99 0.821。对称放大框（不封顶）时明显变差：B3 框 R=0.12 下 >0.80 占 15.6%，gripper_push 起点 >0.78 占 18.5%，物体离基座最远 0.807。**加 `x_cap = 0.11`（goal/候选/方块中心 x ≤ 0.11，与 V5 演示段 goal 的 x 上界相同）后，三档 >0.80 的比例回到 4.4～6.0%，gripper >0.78 ≤ 0.7%，物体最远 ≤ 0.746。** 注意：V5 规划期 `g3_calib.out` 发现这个代理与实际成败**并不单调**（失败条目的中位值 0.686 反而低于成功条目的 0.780），所以它只能当「不比 V5 更差」的护栏，不能代替模拟器实测。
- **杆**：杆根在 |y| ∈ [0.15, 0.25]，杆身长 0.2。框的 y 外扩后，方块会更多地生成在杆身上：**V5 本身就有每段 2.7% 的方块与杆身初始重叠**（离线 OBB 判定；V5 没有杆-方块避让），放大框后升到 3.4～6.0%。用 `peg_gap 0.04` 同时查候选与最终位置后降到 **0.00%**。只查最终位置（不查候选）会有 0.7～1.6% 的局方块最终 256 次耗尽（`variants.out` 里「T1/T3 + peg_gap 0.04」行），所以**候选处必须一起查**，候选再加 0.02 余量。实现上最终位置可以直接走 `spawn_random_cube` 现成的 `avoid=[(c, A, h)]` 预制 OBB 路径（杆身 OBB 加 pad），候选循环是 MoveCube 内部的局部函数，要自己补一条判据。
- **goal 圆盘压在杆下**：goal 没有碰撞，只是画面遮挡。V5 为 3.9%/段，三档升到 4.9% / 6.9% / 10.1%。是否要求 goal 与杆也保持距离，列为待决项。

## 五、四种「往外推」实现的对比（`grid.out`、`variants.out`、`final.out`、`ring.out`）

| 方案 | 效果 | 问题 |
|---|---|---|
| (a) 只加大 R | 见第三节 | 上限 0.07；执行段 goal 被压到 4 个角 |
| (b) 方框放大 + 圆禁区（`final.out` 的 T1/T2/T3：框 0.09/0.12/0.12、0.11/0.13/0.13、0.13/0.15/0.15，R 0.08/0.10/0.12，均带 x_cap 与 peg_gap） | 20000/20000；执行段 goal 半径中位 0.092 / 0.113 / 0.134 | 方框减去圆 = **4 个角浓、四边中点稀**（热图峰值集中在四角），外推主要体现在角上 |
| (c) 环带 `[R_in, R_out]`，框半宽 = R_out（`ring.out`） | 20000/20000；goal/方块半径均匀分布在环内，热图是完整的一圈（+x 侧被 x_cap 截平）；可达性代理最好（peg_push >0.80 为 3.3～4.5%） | 多一个参数 `R_out`（按中心判的同一类拒绝，改动面与 (b) 相同） |
| (d) 加大两两最小距离 | `min_cg` 0.10→0.12/0.14/0.16 让方块到 goal 距离的 p10 从 0.12 升到 0.14/0.16/0.19 | 只是把演示变长，不是「往外推」；可达性代理变差（T3 +min_cg 0.16 时 >0.80 占 16.8%）。**不推荐当主轴**；`peg_gap` 这种「方块离杆」的最小距离是必须加的（修缺陷） |

**推荐 (c)**。理由：用户说的「往外推」是指「物体离桌面中心更远」，环带能让三档之间的半径分布**不重叠地逐档外移**（[0.08,0.12] → [0.10,0.14] → [0.12,0.16]）；方框方案的半径分布是一条长尾，而且浓在角上。

## 六、推荐的 3 档参数（如果 MoveCube 要加档）

两段（演示/执行）用同一套参数；杆仍只查内半径；`x_cap = 0.11`，`peg_gap = 0.04`（候选再 +0.02）；预算沿用 128/256/128/256；`min_cg` 沿用 0.10。

| 档 | 环带 `[R_in, R_out]`（m） | goal 中心框半宽（两段；对应 `region_half_size` = 半宽 + 0.04） | 方块候选半宽 | 布局成功（20000 局） | goal 单次拒绝（实测） | 方块-goal 距离均值 / p90 | peg_push >0.80 | 杆-方块重叠 | goal 压杆/段 |
|---|---|---|---|---|---|---|---|---|---|
| V5 xhard（基线） | [0.05, ∞) | 演示 0.11 / 执行 0.06 | 0.10 | 20000/20000 | 16% / 54% | 0.156 / 0.205（演示），0.136 / 0.171（执行） | 3.6% | 2.68% | 3.9% |
| T1 | [0.08, 0.12] | 0.12（`region_half_size` 0.16） | 0.12 | 20000/20000 | 约 58% | 0.166 / 0.207 | 3.3% | 0.00% | 4.9% |
| T2 | [0.10, 0.14] | 0.14（0.18） | 0.14 | 20000/20000 | 约 66% | 0.189 / 0.243 | 4.4% | 0.00% | 6.9% |
| T3 | [0.12, 0.16] | 0.16（0.20） | 0.16 | 20000/20000 | 约 73% | 0.212 / 0.280 | 4.5% | 0.00% | 10.1% |

- 三档每局平均尝试次数（`ring.out`）：goal 2.4～3.7；方块候选 3.9～6.0，最坏 94/128（T3 演示段）；方块最终 1.6～1.8。条件耗尽概率见第七节。
- 杆的每段平均尝试 1.10 / 1.17 / 1.29，最坏 8/128；杆离圆心最近点的中位数 0.166～0.174。
- 如果只做「xhard 往外推」一档（不加 3 档），建议直接把 xhard 改成 T1 或 T2（待决项 2）。

## 七、预算尾部（`budget_tail.out`）

每个方案 1500 局 × 2 段。对已接受的 goal 和杆，用 4000 个点数值估计方块候选的单次接受率 p（同时满足 |c−g|>min_cg、环带、x_cap、离杆距离），再求 128 次预算的耗尽概率 (1−p)^128：

| 方案 | p 均值 | p 的 p1 | p 最小 | 期望耗尽 | 最坏段耗尽 |
|---|---|---|---|---|---|
| V5 xhard | 0.467 | 0.376 | 0.364 | 2.8e-28 | 7.7e-26 |
| 方框 T1 / T2 / T3 | 0.386 / 0.302 / 0.239 | 0.247 / 0.190 / 0.133 | 0.216 / 0.149 / 0.100 | 5.7e-17 / 5.4e-13 / 2.0e-9 | 3.1e-14 / 1.2e-9 / 1.4e-6 |
| **环带 T1 / T2 / T3（推荐）** | 0.262 / 0.218 / 0.172 | 0.161 / 0.138 / 0.106 | 0.114 / 0.116 / 0.081 | 8.8e-11 / 2.5e-10 / 3.6e-8 | 1.9e-7 / 1.4e-7 / 2.2e-5 |

goal 的 256 次预算：实测单次拒绝约 58%～73%，耗尽概率 < 1e-35。杆的 128 次预算：单次拒绝 ≤ 约 23%，最坏 8 次，可以忽略。
**结论：环带 T3 最坏的那一段耗尽概率约 2e-5，按每档正式生成几十到几百局估算，整批出现一次耗尽的概率 < 1%；即使耗尽，也会抛真 `SceneGenerationError`，由 H4 递补兜住。不需要调大预算。**

## 八、演示时长、fail_safe 与成功判据（问题 4）

- v5-01 三局 h5（`h5_frames.py`）：seed 5400000 总 481 帧（演示 263 / 执行 218）；5400300 总 281 帧（167/114）；5400600 总 280 帧（170/110）。V5 S3c 的 13 局演示是 258～685 步（peg_push 最长）。
- 方块-goal 距离均值从 0.14～0.16 升到 0.17～0.21（最多 +55%）。就算整局按同样比例变长，685 × 1.6 ≈ 1100 帧，也远低于 `RecordWrapper` 的 `fail_safe_limit = 5000`，**不需要动录像器**（录像器按记忆规则冻结）。
- 成功判据：`is_obj_pushed_onto` 的阈值为 `cube_half_size×2×1.2 = 0.048`（peg_push / gripper_push），`is_obj_dropped_onto` 为 0.05（grasp_putdown），都是水平距离、与位置无关，往外推不改判据。风险在于**动作执行**：远处 IK 精度下降、peg_push 需要侧向偏移 0.1，路点更靠外，可能导致 PlannerExhausted 或推偏。V5 的失败已经集中在 peg_push（S3c 13 局里 2 例失败都是任务类）。

## 九、原三档梯度（问题 3）

- `MoveCube.configs = {easy: config_native, medium: config_native, hard: config_native, xhard: config_xhard}`，三档是同一个对象；`NATIVE_SAMPLING`（goal 区域、方块拒绝预算等）不分档；`difficulty` 只在 xhard 分支生效。**原版没有任何按档变化的字段。**
- 所以按用户「给有梯度的任务加 3 档」的口径，MoveCube 可能不在范围内。如果仍要加，梯度建议是：主轴用环带内外半径逐档外移（第六节）；可选副轴是 `min_cg` 逐档加大（0.10/0.12/0.14，演示更长）、`peg_yaw` 保持 ±π。

## 十、实施注意（给 V6 计划）
