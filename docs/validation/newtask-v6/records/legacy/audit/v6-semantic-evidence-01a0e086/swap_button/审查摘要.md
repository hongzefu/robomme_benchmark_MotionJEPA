# ButtonUnmaskSwap 离线语义与视觉核验

审计源码固定为 `0a3f989b0dfcff12a3cbb34a8112cb56864c7ee8`。本目录检查器仅用语法树读取冻结源码、读取正式交付清单列出的 HDF5，不导入仓库模块、不创建环境、不执行 reset 或仿真。12 个 HDF5 的完整 SHA-256 与字节数全部重新计算，并与交付清单核对相同。

## 已确证问题一：按钮动作选择与演示像素目标反转

`ButtonUnmaskSwap::_initialize_episode` 的第一按钮任务绑定 `button_right`，第二绑定 `button_left`；`vqa_options::_options_button_unmask_swap` 的 A／第一按钮绑定 `button_left`，B／第二按钮绑定 `button_right`。`RecordWrapper::_resolve_choice_label` 按文字映射标签，`OraclePlannerDemonstrationWrapper::_execute_selected_option` 执行选项的按钮闭包，像素参数不能纠正这个无参数按钮选项。

真实样例：`xhard1 / episode 3 / seed 8700300`，`timestep_0` 保存 `choice=A, point=[66,149]`、`grounded_subgoal=press the first button at <64,149>`；`timestep_119` 保存 `choice=B, point=[65,107]`、`grounded_subgoal=press the second button at <63,105>`。坐标顺序为行、列，第一目标在画面右按钮，第二在左按钮。对应原图为本目录 `ep3_timestep_0.png` 与 `ep3_timestep_119.png`。

四个新档的12局均保存上述 A→第一、B→第二的标签序列。两个按钮的完成函数接受任一未按按钮，因此左右顺序反转不必造成程序失败，不能拿终态成功证明选择标签与动作、视觉目标一致。

固定祖先 `903cfcc3f2b0a4d040f9bebedb64e0ffd35d3281` 已有同样反转；其环境只有原难度定义、没有 `config_xhard`，故原 hard 也受同一实现影响。这是历史问题延续，不是 V6 新引入。检查器没有读取祖先之后的移动分支，也没有执行历史环境；祖先实际数据的受影响总数未测。

## 已确证问题二：在线抓取目标坐标在交换后没有刷新

`segmentation_utils::process_segmentation` 只在 `current_subgoal_segment != previous_subgoal_segment` 时重新计算坐标。`ButtonUnmaskSwap::_solve_press_then_wait_swaps` 等待交换结束，但在线子目标在按下第二按钮后已经推进到抓取；此时缓存的目标容器坐标会继续随交换移动，文本不变导致缓存不更新。

同一 ep3，`timestep_175` 在线蓝色目标为 `<126,118>`；`timestep_268` 开始实际首抓，`grounded_subgoal` 为 `<135,179>`，`grounded_subgoal_online` 仍为 `<126,118>`。此时旧点落在画面另一容器，见 `ep3_timestep_268.png`；交换中图为 `ep3_timestep_175.png`。

| 难度 | 首抓字段坐标不同 | 对照局数 | 没有该差异的身份 |
| --- | ---: | ---: | --- |
| xhard1 | 2 | 3 | episode 6 |
| xhard2 | 3 | 3 | 无 |
| xhard3 | 3 | 3 | 无 |
| xhard4 | 2 | 3 | episode 3 |
| 合计 | 10 | 12 | 两局 |

12局末帧 `is_completed` 均为真。10/12是首抓时两个标注字段不一致的数量，不是任务失败数，也不是所有帧的错误比例。已目视核验代表局，不将字段不同直接外推为每一局每一帧的像素错误。上游在线/离线时机不同本身允许存在；本项问题是目标已移动后仍使用旧坐标。
