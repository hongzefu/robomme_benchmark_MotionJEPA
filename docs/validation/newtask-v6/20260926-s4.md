## 两次编排事故与处置

第一项事故：代理在xhard4生成中把纯CPU候选回传作为shared GPU短步骤执行；该集群短步骤收尾将仍在运行的长步骤GPU切回独占，导致Vulkan设备初始化失败。两组0 reset／0轨迹调度对照复现：shared短步骤结束后观察到`Exclusive_Process`，纯CPU `--gres=none`短步骤结束后保持`Default`。责任在本轮代理运行编排，不归咎seed、环境或显存OOM。xhard4原96派发明确为26成功、2任务失败、60设备初始化失败、8取消时无结果；只取消工作负载step，保留hold。事故证据与精确时间线见`artifacts/newtask-v6/s4-launch/incident/README.md`及其两份模式观察日志。

第二项事故：A席回传脚本运行中被原地修改，已输出两档`TRANSFER_DONE`后仍发生`line 32: f: command not found`，整个脚本退出127。不得把“两档复制结束”改写为“回传脚本退出0”。随后按既有源清单逐档SHA核验，确认实际本机内容完整，不自动重传或覆盖；运行中的脚本随后冻结。B席后处理退出0。这些原始异常与失败文件全部保留，后续只使用独立新版本控制脚本。

S2之后的接续门曾因Counter省略零值引发`KeyError`，当时S3／S4未启动；其记录保留在[接续报告](20260926-resume.md)，不混入上述S4真实派发计数。所有事故处置均未通过改成功定义、放宽比较阈值或删除失败来获得当前165成功。
