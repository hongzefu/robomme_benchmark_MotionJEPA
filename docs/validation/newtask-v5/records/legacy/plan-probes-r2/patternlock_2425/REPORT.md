## 做法

- worktree `/data/hongzefu/robomme_v5_probe_wt`（581efec），`PYTHONPATH` 指向其 `src`，主仓 `.venv`；未改任何被跟踪文件，结束时两个树 `git status --short` 都为空。
- **搜索层**（`search_probe.py`，纯 CPU、单进程）：逐句复刻 `PatternLock._load_scene` 的抽签循环——`torch.Generator().manual_seed(seed)` →
  `randperm(25)[:2]` → 真实的 `utils/adjacent.py::find_path_0_to_8(R=C=5, diagonals=True)` → 判长度，预算 20000。
  三个目标区间各自独立试验：`[24,24]`、`[25,25]`、`[24,25]`（后者就是 V5 实际规则）。第一轮每组 200 次（`search_probe.json`），
  因为很快又加跑了每组 1000 次（换 seed 段，`search_probe_1000.json`）。1000/5000/10000 预算下的命中率由同一序列截断得到（同 seed 下完全等价）。
- **演示层**（`demo_probe.py`）：进程内补丁 `PatternLock.configs["xhard"]={"grid":5,"length":[24,25]}`、模块级
  `NATIVE_SAMPLING[...]["max_attempts"]=20000`；reset 后若节点数不在 [24,25] 即抛错（模拟 V5 的耗尽抛错）。
  录制链路与 V4 实跑同口径：官方 `generate_dataset._planner_classes`（screw 3 次 + RRT* 3 次）+ `_execute_tasks` + `RobommeRecordWrapper`，
  不开 recover、不注入 spec。GPU 0、8 局串行。帧数全部从 h5 的 `info/is_video_demo` 数出，逐段按 `is_subgoal_boundary` 切。
- **交叉核验**：离线复刻循环对这 8 个 seed 算出的命中尝试次数（107/141/34/564/115/27/108/164）与环境内 `actions.path_attempts` 逐个相等，
  说明离线统计与真实 reset 的抽签完全同分布。

- 单次 DFS 尝试 0.137～0.138 ms（计划里估的「毫秒级、20000 次十几秒」偏保守，实际 20000 次满打满算约 2.8 s）。

  [25,25] 约 e^(−20000/2372) ≈ 2×10⁻⁴；[24,24] 约 e^(−46)；[24,25] 约 e^(−58)，即 **V5 规则下「耗尽抛错」实际不会发生**。
- ⚠ **[24,25] 区间下节点数不是均匀的**：循环在第一次落入区间时就停，24 节点远比 25 节点常见，1000 次里 24 节点 863、25 节点 137（13.7%）；
  首轮 200 次为 172 / 28。所以正式局大多是 24 节点（23 段）。

## reset 墙钟与抽签「10 条成功、最多 30 次」

- 路径搜索在 `_load_scene` 里，是 reset 的一部分。V5 规则 [24,25] 下搜索本身 p95 0.14 s、最大 0.38 s（单线程无竞争口径），
  相对 PatternLock 一次 reset/建场景的秒级开销可忽略；本脚本记录的 `reset_wall_s≈0` 是因为场景在 `gym.make` 时已构建，
  整局（建环境 + 演示 + 执行 + 写 h5/视频）66～83 s。
- 耗尽概率 ≈ 0，且 PatternLock 无其他新增拒绝点 ⇒ **抽签 10 次即得 10 条，对 30 次上限零影响**。若改成只要 25 节点 [25,25]，
  每次 reset 耗尽概率约 2×10⁻⁴，30 次内仍几乎必成，但搜索墙钟 p95 升到约 0.93 s、最大约 2.2 s。

## 盲区

1. 演示只跑 8 局（25 节点仅 2 局），带外比例 1/8 的置信区间很宽；每段帧数随路径方向组成波动大，未做大样本演示或离线 screw 模型批量估计。
2. 搜索墙钟为本机单进程无竞争测得；正式抽签多 worker 并发时会放大，但量级仍是亚秒。
3. 「耗尽抛错」只以 reset 后判节点数模拟，未验证真实代码里 `for…else` 抛 `SceneGenerationError`（依赖 L3 遮蔽修复）的实际类型与上层捕获。
4. 未经 spec 回注通道（`native_episode_spec`）与 header 冻结 `max_attempts` 决策键；只验证了原生抽签路径。
5. 未检查视频文件内容，只以 h5 为准；演示 oracle 在单 worker 下跑，多 worker 下 RRT 墙钟预算的分叉未覆盖。
