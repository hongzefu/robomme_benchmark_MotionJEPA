1013-mixed8-400ep-plan.html — 八档难度循环 400 条全任务数据集：生成器扩展、H5 校验、多 worker 测速

权威性：本文件是「八档难度循环 400 条数据集」的唯一现行计划；1006 计划与 1012 系列只作 xhard 子类与配置表的来源，「从母 seed 派生」不再是全量生成方式。

代码锚点：/data/hongzefu/robomme_benchmark_newtask-v3-MotionJepa1006，分支 newtask-v3-MotionJepa1006，本版撰写时 HEAD 8bfd3eed（2.112）。生成器 scripts/data-generation-newSeed/generate_dataset_newseed.py，seed 公式 seed_layout.py，xhard 子类 src/robomme_xhard/。原版数据集本机副本 /data/hongzefu/robomme_data_h5/（HF Yinpei/robomme_data_h5 revision a5e4e25，AGENTS.md P3）。

commit 体例：<大>.<小> 中文描述，本版为 2.113（按 2.111 版的对抗审计与用户裁决修订），之后的提交从 git log 最近一次顺延；子代理提交前缀 sub/<编号>: 。外部依赖：ManiSkill 钉 07be6fbc 不动；src/robomme/ 零改动（P1）。

〇、为什么做

现行 xhard 生成从官方 hard 母 seed 派生，母清单每任务只有 2 个 seed，最大一轮 180 张卡，从未对准「每任务 400 条」。用户要的数据集是每任务 400 条、easy／medium／hard／xhard12…xhard20 八档固定均分、xhard 也按 seed 公式自算。旧比例模式已具备 400 条接续、重试、进程池、metadata 骨架，主体改动在生成器（循环允许 xhard 值、xhard 作业走 <Task>XHard、FailRecover 按 base 档序号、崩溃产物隔离），另需 seed_layout.py 加两个解析函数、测速脚本加内存探针与停档机制、src/robomme_xhard/tools/ 新增校验工具——这超出 P2「只改两处」，已由用户批准扩展（K17，红线 R11）。配套一套 H5 校验（100 个样本、四条校验判定行、全量身份对账）和一套多 GPU 测速阶梯。压缩不做。

三、机制

3.1 八档循环、缺档与 FailRecover

新参数 --difficulty-cycle easy,medium,hard,xhard12,…,xhard20，与现有 --difficulty 互斥。每个任务把配置表里没有的 xhard 档剔掉得到自己的有效循环，按 episode % len 取档；400 不整除时多出的条数落在循环最前面几档。FailRecover 只给原版带 FailRecover 的 11 个任务（K11），按 base 档（easy／medium／hard）的绝对序号 r 分配：r = 该任务 ep0 到 ep(e−1) 中 base 档 episode 的个数，r≤2 为 z、3≤r≤5 为 xy，与 --episode-start、接续生成无关；xhard 一律不设。每任务 3+3 条，与原版每 100 条 3+3 的数量相同，占比从 6% 降到 1.5%（K11 b 甲）。

3.2 xhard 走公式 seed，失败与崩溃怎么处理

xhard 作业的 gym_id 为 <Task>XHard，其余字段与 easy／medium／hard 作业相同：seed 由公式算、任务性失败 attempt+1 换 seed，八档统一上限 --max-attempts 100（K10）。子类把母配置复制后叠旋钮，录像器写进 h5 的 setup/difficulty 就是 xhard14 这类值；母清单模式与旧比例模式行为不变。循环模式另补三处骨架缺口（只在循环模式生效）：①进程池崩溃时被连带退回的作业也计入「连续非任务性失败」，第 3 次放弃；②崩溃时 worker 已写的 h5／视频加 CRASHED_ 前缀移出成功集合后再重试（K12），保证每个 episode 只有一份成功 h5；③xhard 作业的拒绝证据与 swap_plan、runtime_checks、xhard_knobs 写进结果记录，供语义校验读取。产物形态不变：每 episode 一个无压缩 h5（实测 xhard14 一条 660 timestep 约 420 MB）。

3.3 H5 校验与身份对账

样本是每任务每个有效档的第一条，共 100 个文件，正好落在 smoke 二的 ep0–7 里：本机先正式判一次，AWS 全量后对它自己的 100 个再判一次。golden schema 从原版副本 /data/hongzefu/robomme_data_h5/ 每任务 episode_0 导出一次并提交进 git，剔除上游 68a65a0 删掉的字段；AWS 上只用这 16 份 JSON。setup/task_goal 的列表长度合法地随分支变化（VideoPlaceButton base 4 条、xhard 3 条；PickXtimes 1 或 2 条），golden 对它只比维数、dtype 与非空，不比长度。抽样之外，另对全部产物做一次轻量身份对账，预期值由冻结配置与公式独立算出，不读产物自己写的 effective_cycles。第一次校验不论 PASS／FAIL 都完整报告，FAIL 不动文件；之后是否上 AWS 由用户决定（K16）。

3.4 测速：先量内存，再跑阶梯

测速分两步。第一步内存探针 P8：卡 0 上 8 个 worker，跑八档任务中 6 个（BinFill、PickXtimes、SwingXtimes、VideoUnmaskSwap、ButtonUnmaskSwap、VideoRepick）的 ep6–7 外加 PatternLock、RouteStick 的 ep6–7，即全部是最重的 xhard18／xhard20，共 16 条；记单 worker 峰值内存 R（GB）、卡 0 峰值显存除以 8 得单 worker 显存 V，以及本机实测可用内存 M、单卡显存 G。第二步阶梯：档位 L32（卡 0–3，每卡 8）、L64（卡 0–7，每卡 8）、L128（卡 0–7，每卡 16），L48 按用户原话跳过；每档 16 任务各 24 条共 384 条，八档全部覆盖，且 384 > 2×128+1，三档都能剔除首尾得到真正的稳态窗口。每档起跑前做准入：W×R×1.2 + 40 ≤ M 且 (W/卡数)×V×1.2 ≤ G，不满足就不跑、记 skipped_by=mem_budget。运行中三道闸：生成器开关 --stop-on-pool-crash（第一次池崩溃即自停、非零退出）、可用内存低于 40 GB、单档超 90 分钟；任一触发都整组终止该档进程并停住阶梯。W* 取所有跑完且稳态窗口有效的档中，稳态吞吐达最高值 97% 的最小 worker 数。

判定 CALIB=PASS probe_rss_gb=<R> probe_vram_gb=<V> cells_run=<n> skipped=<档名|none> best_workers=<W*> crashed_at=<W|none>；PASS 条件：P8 跑完且 L32 跑完、稳态窗口有效。

3.5 新机器（AWS 8 卡）接入

用户启动 AWS 后：①在 AWS 上只读跑 AGENTS.md 第 0 条判定命令（此时还没有仓库，命令块从本计划复制），输出交回；②vail 主会话据此写 AGENTS.md 环境 C 列与 P7 环境 C 条文（K17），提交并 push，记下该提交 SHA；③AWS git clone 后 git checkout --detach <SHA> 并核对 git rev-parse HEAD，uv sync --frozen --extra dev（能联网，K18），核验 editable 指向 src/、渲染探针、磁盘余量 ≥ 2 TB、复跑 smoke 一。git 提交只在 vail：Beta commit 也在 vail 打（body 写入测速得到的 W*、GPUS*），AWS fetch 后检出该 SHA、git status --short 为空才起跑；留档 rsync 回 vail 提交。AWS 不下载原版数据集；跨机器对拍只需把 vail smoke 二中那 100 个样本（按 check.json 的样本清单挑，约 25–40 GB）rsync 过去。产物持久化由用户负责（K18）。

一、机制细节

1.1 循环解析与有效循环

seed_layout.parse_difficulty_cycle(text, xhard_values)：逗号分隔、去空白、小写；每项 ∈ DIFFICULTY_ORDER ∪ xhard_values，否则 SeedLayoutError；允许重复；空串报错。seed_layout.filter_cycle(cycle, available_xhard)：剔除不在集合内的 xhard 项，结果为空报错，保持顺序与重复。difficulty_for 不改。生成器父进程用 importlib.util.spec_from_file_location 独立加载 src/robomme_xhard/configs.py（纯数据表，只有 from __future__）取 DIFFICULTIES 与 TIER_CONFIGS 键，不 import robomme_xhard；worker 内导入仍在绑卡与 import robomme.robomme_env 之后（P2）。

episode 到难度（前 12 条）：8 档任务 easy,med,hard,x12,x14,x16,x18,x20,easy,med,hard,x12；VideoUnmask（4 档）easy,med,hard,x14,easy,…；MoveCube（3 档）easy,med,hard,easy,…。最大 seed 16×1000+399×100+99 = 55999，低于 test 布局 offset 500000；不同任务 seed 数值重叠是 400 条先例已有情况，seed 只需任务内唯一。

1.2 FailRecover 按 base 档绝对序号

生成器新增常量 FAIL_RECOVER_TASKS = 原版带 FailRecover 的 11 个任务（BinFill、PickXtimes、SwingXtimes、VideoUnmask、ButtonUnmask、VideoUnmaskSwap、ButtonUnmaskSwap、PickHighlight、VideoRepick、VideoPlaceButton、VideoPlaceOrder；2026-10-13 只读核对原版 ep0–7：这 11 个为 ep0–2 z、ep3–5 xy，其余 5 个无 fail_recover_mode）。EpisodeJob 新增 recovery: str | None = "auto"（"auto" 为哨兵，旧模式沿用骨架的 episode 号规则）。循环模式下父进程对每个作业按 r(e) = |{e' < e : cycle[e' % len] ∈ base}| 赋值：任务不在 FAIL_RECOVER_TASKS 或作业是 xhard → None；r≤2 → "z"；3≤r≤5 → "xy"；其余 None。r 只依赖任务的有效循环与绝对 episode 号，与 --episode-start、本次建了哪些作业无关。bump 用 replace 保留该字段。run_parameters.json 写 recovery_assignment（每任务 z 与 xy 的 episode 号，覆盖 0..399 全序列）。

1.3 xhard 作业、池崩溃与产物隔离

EpisodeJob 新增 xhard_values: tuple[str, ...] = ()，属性 is_xhard = difficulty in xhard_values、cycle_mode = bool(xhard_values) or 循环模式标记；gym_id = make_name or (f"{task}XHard" if is_xhard else task)。card_role／make_name／source_difficulty 保持 None，fixed_seed 为假。_pool_init 的 xhard_mode 在循环含 xhard 时为真；_worker 导入条件 job.card_role is not None or job.is_xhard；save_video 断言与证据采集条件扩为 job.fixed_seed or job.is_xhard，证据键在 swap_plan、runtime_checks 之外加 xhard_knobs（unwrapped.xhard_knobs）与 xhard_label；_exception_evidence 条件同样扩为 fixed_seed or is_xhard，初始化阶段的拒绝也留下 stage／rejection／detail。

失败处理（循环模式）：五类任务性异常与 xhard 运行期拒绝 → attempt+1（拒绝卡的已写产物沿用 FAILED_ 前缀）；_run_jobs 池重建支路对每个被退回的在途作业同样 strikes[key]+=1，达到 3 即 exhausted；新增 _isolate_crashed_card(job)：池重建或非任务性失败时，若该作业的成功名 h5／视频已存在，改名加 CRASHED_ 前缀并把路径写入结果记录，再按上面规则重试。成功集合只认无前缀文件。新增 CLI 开关 --stop-on-pool-crash（默认关）：开启时第一次发现池损坏即停止派发、shutdown(cancel_futures=True) 关闭全部池、隔离在途产物、写 run_summary.json 的 stopped_by="pool_crash" 与崩溃时完成数，以退出码 3 结束。

六、风险登记

风险影响对策
xhard 子类在公式 seed 上的通过率未知（只在每任务 2–10 个母 seed 验证过；swapv3 一轮 180 卡失败 50 张）重试把全量耗时抬高数倍，个别 episode 可能用尽 100 次G4 报告尝试次数表；全量 PARTIAL 交用户（K10）
AWS 核数与内存未知L128 可能因 CPU 争用而无收益，或被内存准入跳过探针与准入先挡；W* 只从跑完的档里选
全量不设运行期内存护栏W* 档若在全量中途遇更长尾的 episode 可能吃紧W* 已过准入（含 1.2 余量与最重档探针）；Monitor 盯 out of memory、进程池已损坏
importlib 独立加载 configs.py 若将来加包内导入会失效父进程 ImportError用例守住；失效即报错不回退
golden 与现生成器字段差异超出 excluded_keys 与变长白名单H5_SCHEMA FAIL第一次校验暴露并报告；白名单增项先告知用户
FAILED_／CRASHED_ 残留占盘全量盘占用上浮smoke 二统计残留体量；超过 smoke 二总量 10% 报告用户
