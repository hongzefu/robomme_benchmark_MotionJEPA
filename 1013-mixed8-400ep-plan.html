1013-mixed8-400ep-plan.html — 八档难度循环 400 条全任务数据集：生成器扩展、H5 校验、多 worker 测速

权威性：本文件是「八档难度循环 400 条数据集」的唯一现行计划；1006 计划与 1012 系列只作 xhard 子类与配置表的来源，「从母 seed 派生」不再是全量生成方式。

代码锚点：/data/hongzefu/robomme_benchmark_newtask-v3-MotionJepa1006，分支 newtask-v3-MotionJepa1006，撰写时 HEAD 6ce0bb66（2.110）。生成器 scripts/data-generation-newSeed/generate_dataset_newseed.py，seed 公式 seed_layout.py，xhard 子类 src/robomme_xhard/。原版数据集本机副本 /data/hongzefu/robomme_data_h5/（HF Yinpei/robomme_data_h5 revision a5e4e25，AGENTS.md P3）。

commit 体例：<大>.<小> 中文描述，本计划修订为 2.111；子代理提交前缀 sub/<编号>: 。外部依赖：ManiSkill 钉 07be6fbc 不动；src/robomme/ 零改动（P1）。

授权边界：只规划不实施。开工令按 AGENTS.md 第 2 条；开工前先派审查子代理出 PLAN_CONSISTENCY_REVIEW。本机 sled-vail 只做代码实现、smoke 与 100 样本校验；测速与全量换 AWS 8×A100 机器，开工前先补 AGENTS.md 第 0 条环境 C 列。

〇、为什么做

现行 xhard 生成从官方 hard 母 seed 派生，母清单每任务只有 2 个 seed，最大一轮 180 张卡，从未对准「每任务 400 条」。用户要的数据集是每任务 400 条、easy／medium／hard／xhard12…xhard20 八档固定均分、xhard 也按 seed 公式自算。旧比例模式已具备 400 条接续、重试、进程池、metadata 骨架，只差「循环允许 xhard 值」与「xhard 作业走 <Task>XHard」两处，因此只扩展生成器。配套一套简版 H5 校验（100 个样本、四条判定行）和一套多 GPU 测速阶梯。压缩不做。

三、机制

3.1 八档循环、缺档与 FailRecover

新参数 --difficulty-cycle easy,medium,hard,xhard12,…,xhard20，与现有 --difficulty 互斥。每个任务把配置表里没有的 xhard 档剔掉得到自己的有效循环，按 episode % len 取档；总数恒为 400。FailRecover 不再按 episode 号，而是按该任务 base 档（easy／medium／hard）episode 的序号：前 3 条 z、接下来 3 条 xy，xhard 一律不设，官方「3 加 3」的数量保持。

3.2 xhard 走公式 seed

xhard 作业的 gym_id 为 <Task>XHard，其余字段与 easy／medium／hard 作业完全相同：seed 由公式算、失败 attempt+1 换 seed、非任务性失败连续 3 次放弃。子类把母配置复制后叠旋钮，录像器写进 h5 的 setup/difficulty 就是 xhard14 这类值；母清单模式与旧比例模式一行不改。产物形态不变：每 episode 一个无压缩 h5（实测 xhard14 一条 660 timestep 约 420 MB）。

3.3 H5 校验

样本是每任务每个有效档的第一条，共 100 个文件，正好落在 smoke 二的 ep0–7 里，所以本机先正式判一次，AWS 全量后对它自己的 100 个再判一次；两台机器同 seed 的 100 条另做 joint_action 逐元素对拍，只报最大差、不设闸门。golden schema 从原版副本 /data/hongzefu/robomme_data_h5/ 每任务 episode_0 导出一次并提交进 git，剔除上游 68a65a0 删掉的 8 个字段并把清单写进 golden；AWS 上不需要原版，只用这 16 份 JSON。FAIL 只报告不动文件。

3.4 多 GPU 测速阶梯

生成器已是每卡一个进程池、worker 均分到各卡，测速脚本的档位格式本来带 gpus 字段，不需要新机制；只加 --difficulty-cycle、--affinity 透传、内存护栏与池崩溃自停。AWS 上的档位：32 worker 用卡 0–3、48 用卡 0–5、64 与 128 用卡 0–7，每档 16 任务各 4 条，吞吐取稳态窗口。物理仿真在 CPU，p4d.24xlarge 的 96 vCPU 才是真正上限，128 档预期触护栏，它的价值是钉死崩溃点。判定 CALIB=PASS cells=<n> best_workers=<W*> crashed_at=<W|none>，W* 取全部成功档里稳态吞吐达最高 97% 的最小 workers。

3.5 新机器（AWS 8×A100）接入

第一步只读跑 AGENTS.md 第 0 条判定命令，把主机、GPU、磁盘、ssh 别名写成环境 C 一列提交，并加一条 P7 覆盖：环境 C 的用卡由测速决定、不限 GPU0。然后 clone、uv sync --extra dev、核验 editable 指向 src/、渲染探针、磁盘余量 ≥ 2 TB、复跑 smoke 一。AWS 不下载原版数据集：校验只要 git 里的 golden JSON，跨机器对拍只要 vail 的 100 个样本 h5（约 25–40 GB，rsync 过去）。git 在有凭据一侧操作，AWS 无凭据则留档 rsync 回 vail 提交。

一、机制细节

1.1 循环解析与有效循环

seed_layout.parse_difficulty_cycle(text, xhard_values)：逗号分隔、去空白、小写；每项 ∈ DIFFICULTY_ORDER ∪ xhard_values，否则 SeedLayoutError；允许重复；空串报错。seed_layout.filter_cycle(cycle, available_xhard)：剔除不在集合内的 xhard 项，结果为空报错，保持顺序与重复。difficulty_for 不改。生成器父进程用 importlib.util.spec_from_file_location 独立加载 src/robomme_xhard/configs.py（纯数据表，只有 from __future__，2026-10-13 核实）取 DIFFICULTIES 与 TIER_CONFIGS 键，不 import robomme_xhard，worker 内导入仍在绑卡与 import robomme.robomme_env 之后（P2）。

episode 到难度（前 12 条）：8 档任务 easy,med,hard,x12,x14,x16,x18,x20,easy,med,hard,x12；VideoUnmask（4 档）easy,med,hard,x14,easy,med,hard,x14,…；MoveCube（3 档）easy,med,hard,easy,…。最大可能 seed 16×1000+399×100+99 = 55999 低于 test 布局 offset 500000，现有护栏通过；不同任务 seed 数值重叠是 400 条先例已有情况，seed 只需任务内唯一。

1.2 FailRecover 按 base 档序号

EpisodeJob 新增字段 recovery: str | None = "auto"（"auto" 为哨兵）；属性 recovery_mode：非 "auto" 时直接返回该值，否则沿用骨架的 episode 号规则。循环模式下父进程对每任务按 episode 升序给 base 档作业编序号 r：r≤2 → "z"，3≤r≤5 → "xy"，其余 None；xhard 作业 None。bump 用 replace 保留该字段。旧比例模式与母清单模式不传该字段，行为不变。结果记录已有 recovery_mode 字段，供 SMOKE2 核对落点。

1.3 xhard 作业

EpisodeJob 新增 xhard_values: tuple[str, ...] = ()，属性 is_xhard = difficulty in xhard_values；gym_id = make_name or (f"{task}XHard" if is_xhard else task)。card_role／make_name／source_difficulty 保持 None，fixed_seed 为假。_pool_init 的 xhard_mode 在循环含 xhard 时为真；_worker 内导入条件 job.card_role is not None or job.is_xhard；证据采集与 save_video 断言条件扩为 job.fixed_seed or job.is_xhard。失败处理：五类任务性异常与 xhard 运行期拒绝 → attempt+1（拒绝的卡已写产物加 FAILED_ 前缀保留）；非任务性连续 3 次放弃。

1.4 校验工具

六、风险登记

风险影响对策
xhard 子类在公式 seed 上的通过率未知（只在每任务 2–10 个母 seed 验证过；1012 一轮 180 卡失败 50 张）重试把全量耗时抬高数倍G4 阈值；步骤 5 用户定 xhard --max-attempts
AWS 实例型号与存储未定（K9 按 p4d.24xlarge 假设；实例 NVMe 停机即清空）档位整除、内存护栏阈值、1.6 TB 落点都可能要改ENV_C 判据表先定硬件；产物落点由用户在接入前决定（EBS／S3／HF）
多卡下 --affinity per-gpu 把 96 核按卡切分，4 卡档每卡 24 核、8 卡档每卡 12 核L32 用 4 卡时每卡 8 worker 占 24 核，CPU 利用率偏低但不崩吞吐以稳态窗口为准；若 L32 明显低于单卡经验值，在 calibration.md 标注并交用户
importlib 独立加载 configs.py 若将来加包内导入会失效父进程 ImportError用例守住；失效即报错不回退
golden 从原版导出而现生成器少 8 个字段、xhard 子类可能多字段extra／missing 误报excluded_keys 固定清单；真有差异在第一次校验暴露，交用户
FAILED_ 前缀 h5 残留占盘全量盘占用上浮smoke 二统计残留体量，超预期交用户决定是否加清理开关（新方案调整）
两台机器 commit 分叉历史混乱git 只在有凭据一侧操作
