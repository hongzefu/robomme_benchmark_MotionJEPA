三、机制

3.1 五组 seed 区间与每格 12 条

生成器循环模式的 --episodes 对一次调用里的全部任务统一，而各任务的有效 xhard 档数不同（TIER_CONFIGS 缺档剔除：StopCube 没有 xhard12，PickHighlight 只有 12／16／18，VideoPlaceButton 只有 12／14，VideoUnmask／ButtonUnmask 只有 xhard14，VideoPlaceOrder 只有 xhard12）。要让每格恰好 12 条，就按档数把 14 个任务分成五组，每组一次调用、--episodes = 12 × 档数。难度取 有效循环[episode % 档数]（seed_layout.py::difficulty_for），从 ep50 起算：G5 的 ep50 落 xhard12（50 % 5 = 0），G4 的 ep50 落 xhard18（50 % 4 = 2），G3 的 ep50 落 xhard18（50 % 3 = 2），G2 的 ep50 落 xhard12；起点落在哪一档不影响每档条数，各档恰好 12。

3.2 失败、崩溃与缺条

xhard 作业的 gym_id 为 <Task>XHard，任务性失败（SceneGenerationError、PlannerExhausted、ScrewPlanFailure、FailsafeTimeout、xhard 运行期拒绝）按 attempt+1 换 seed 重试，上限 100（T10，待确认）；非任务性失败连续 3 次放弃并记 exhausted；池崩溃的已写产物加 CRASHED_ 前缀隔离。耗尽会在 metadata 里留下 episode 空洞，而 S5 的追加工具硬断言「合并后 episode 连续 0..N-1」——有空洞时工具整体拒绝、不落盘。本计划不自行补 seed（P8）：出现耗尽即停在 S5 之前，把缺失清单交用户裁决，不预设自动分支。1013 smoke 二 128 条里唯一的耗尽是 VideoPlaceOrder ep3 xhard12（连续三次非任务性失败），本计划 G1 的 VideoPlaceOrder 是重点盯防对象。

3.4 seed 追加进官方 test metadata

官方 test metadata 是 {"env_id","record_count","records":[{"task","episode","seed","difficulty"}…]}，记录多行缩进、文件结尾无换行；生成器输出的 record_dataset_<Task>_metadata.json 与之同构，difficulty 字段写的就是 xhard14 这类值。追加工具 append_train_metadata.py 已有 --metadata-dir 参数（本计划传 src/robomme/env_metadata/test），三条硬断言：新旧 episode 不重叠、合并后连续、env_id 一致；序列化口径逐字对齐。对抗验证确认它的 --env all 展开为 16 个任务、输入目录缺任一任务的 metadata 即整体拒绝，所以追加必须逐组显式 --env。「纯追加」在 git diff --numstat 上的真实形态：每个文件恰改写两行——record_count 那一行，以及原末条记录的收尾 } 变成 },——即每文件删 2 行、14 个文件合计 28；其余只增不删。判定行据此写成 PROTECTED_APPEND_ONLY=PASS files=14 deleted_lines=28 old_records_unchanged=14 env_id_unchanged=14 added_records=624，由主会话脚本对 14 个文件比对 HEAD 与工作区的 JSON：records[:50] 逐字节不变、env_id 不变、record_count 等于新长度、git diff --name-only -- src/robomme 恰为这 14 个文件。这一步是 P1 受保护目录的改动，范围由用户 T5 界定（14 个 test metadata 的纯追加）。
