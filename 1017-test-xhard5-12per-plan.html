三、生成侧机制（本仓库）

3.1 五组、每格 12 条

循环只含 xhard12,…,xhard20，--layout test --episode-start 50，难度取 有效循环[ep % 档数]（G4、G3 的 ep50 落 xhard18），按档数分五组、--episodes = 12 × 档数。seed = 500000 + env_code×10000 + ep×100 + attempt，同一任务内与官方 ep0–49 零重，上界 670999 低于 val 的 1,000,000。

3.2 失败与缺条

任务性失败 attempt+1 换 seed（T10）、非任务性失败连续 3 次放弃记 exhausted、池崩溃产物 CRASHED_ 隔离——都沿用 1013。耗尽会让 metadata 出空洞，追加工具会整体拒绝；此时停在追加前把缺失清单交用户，不自动补 seed（P8）。

3.3 校验与追加

校验工具加 --layout test --tasks <组内任务> 后每组各跑 check（每格第一条，共 52 个样本）与 audit（全部身份）。追加逐组显式 --env；纯追加在 numstat 上每文件恰删 2 行（record_count 行与原末条的 }），判据按此写；追加后 ep≥50 的难度值是 xhard14 这类，所以任何消费方都必须用 <Task>XHard 建环境——评估侧正是这样做。

3.4 上传与读回校验

本机对 624 个 h5 流式算一次 sha256（校验工具不算 sha，约 0.3～0.4 TB 读盘），上传五组产物、清单与 SHA256SUMS 到新 bucket；HF_UPLOAD=PASS 后主会话在 GL 起 standard 分区纯 CPU job 流式读回比对，先 1 个对象冒烟。这两步是长尾，不阻塞交接。

四、评估侧机制（策略仓库分支）

4.1 一条链路评三个模型

评估是「模型进程 + 仿真进程」两进程：仿真进程按清单逐局用 seed 建环境，把画面与指令经 websocket 发给模型进程、收动作执行，环境判 task_success。三个模型只换模型进程：你的两条 run 用本分支 scripts/training/serve_policy.py --policy.config=mme_vla_suite_b128_80k --policy.dir=<run>/60000（torch；motion 开关由 run 目录里的 history_config.resolved.yaml 快照决定，所以下载必须带 run 级文件）；官方 79999 用 mme-vla ecf086c 检出的 serve_policy.py --policy.config=mme_vla_suite（JAX，零 diff）。仿真进程只有一份：以 927c56d 的清单模式 eval.py 为底，改建环境三处（<Task>XHard、经环境变量读 XHard metadata 副本、check_seed 比清单 difficulty）。两版客户端同源（共同祖先 ecf086c，openpi-client 零差异，websocket 的 reset／add_buffer／infer 字段未改），所以一份客户端能服务三个模型。

4.2 仿真环境与 metadata 来自本仓库 tag

评估分支把子模块 third_party/robomme_benchmark 的 url 改为 hongzefu/robomme_benchmark_MotionJEPA、gitlink 锁 testx-metadata-v1（含 robomme、robomme_xhard 与追加后的 metadata）；客户端起跑断言 robomme.__file__ 与 robomme_xhard.__file__ 都在子模块下。不另建子模块，不用 PYTHONPATH 兜底。

4.3 清单：1200 局，三模型共用

从子模块的 test metadata 导出：每任务每档 episode 升序前 12（easy／medium／hard 从官方 ep0–49 取，xhard 五档就是生成的全部）。8 档任务 96 局、StopCube 84、PickHighlight 72、VideoPlaceButton 60、单档任务 48、MoveCube／InsertPeg 36，合计 1200；两片各 600（按任务分）。清单记 sha256，三轮评估都核对同一个值。

4.6 motion 模型的 encoder 输入与 160 窗预算（T13）

encoder 送入怎么保证对：motion encoder 不读 h5，sidecar 子进程（Wan VAE + MotionJEPA encoder）按 stride 16、window 33 在线切 256 域原始帧，入口硬断言形制；用哪个 encoder 由 run 目录快照 history_config.resolved.yaml（核 sha256 与 motion_provenance.json）决定；sidecar 握手把 VAE／encoder 权重 sha、源码 sha、torch／cuda／cudnn／diffusers 版本、flags 与离线建库的 store_meta.provenance 逐键比对，不等即 raise；motion_protocol.py 两侧 sha 须同一份。历史上在线现算的 240 个运动窗与离线表逐字节一致（策略仓库 docs/train-infer-consistency.md）。本轮只豁免四个硬件键（离线库在 A100 建、本机是 RTX 6000 Ada），接受 encoder 输出跨 GPU 的数值差并留档写明；下载 ckpt 时连带下载 encoder run 目录与新库的 store_meta.provenance。

160 窗怎么处理：预算是 motion yaml 的 budget: 160，推理侧原契约是零截断、超限 raise（整局落成 error）。本轮：① 清单导出前用真实 h5 的 demo 帧数按 eval_es_bound.py 口径算每局窗数（demo 窗 + 1300 步执行窗），报 EVAL_ES_BOUND=DONE max_windows=<n> over=<k>，超限局不剔除；② 评估分支加 MMEVLA_MOTION_OVERFLOW=drop_oldest：合法起点数超 160 时丢最早的起点、保留最近 160 个窗，每步记丢弃数，结果行加 motion_dropped_max，汇总表单列受影响局数；默认值仍为 raise，训练侧与一致性工具不受影响。这是训练未见过的外推，受影响局的成绩只作参考。

⚠ 已知要改一行的地方：motion sidecar 的卡号取自快照 online_gpu（AWS 上写的物理卡号），本分支 policy_config.py 不读 MMEVLA_MOTION_ONLINE_GPU；本机两片各占一卡时 sidecar 必须跟策略同卡，评估分支要让它读该环境变量（legacy-eval README 已记录此坑）。

六、风险

风险处置
某 episode 耗尽（1013 冒烟曾见 VideoPlaceOrder 连续三次非任务性失败）停在追加前交用户，不自动补
同卡上策略进程（JAX／torch）+ 仿真渲染 + motion sidecar 显存不够10k 冒烟先验证；不够则每卡一对、sidecar 同卡，仍不够交用户
add_buffer 段边界状态机对 927c56d 客户端的 exec_start_idx 发送方式报错PROTO_CHECK 在开工前核实；不兼容则客户端按本分支逻辑同步一处并记入 CLIENT_DIFF
两条 run 的 60k bucket 迟到评估任务 depends_on 挂起，先跑官方 2 局冒烟与分支搭建；10k 冒烟只等 512 的 10000
max_steps=1300 对 xhard18／20 偏短沿用官方口径，表里单列 timeout
motion 窗超 160 的局（xhard 长 demo）走 drop_oldest，是训练未见的外推逐局记 motion_dropped_max，汇总单列受影响局；不改 160
豁免硬件键后 encoder 输出跨 GPU 有数值差留档写明；不做跨机逐位对拍
评估耗时远超估计10k 冒烟校准；单轮外推超 10 小时先报用户
客户端子项目依赖重（ms_swift、transformers）解析慢或冲突按 requirements.txt 钉版本；失败记录原始报错交用户

七、盲区

  • 生成器「循环里无 base 档」与校验工具加参数后的行为靠 smoke 与单测证实。
  • 单局评估耗时、同卡三进程显存、两条 run 的 bucket 名与 run 级文件是否齐全，都未实测。
  • 策略分支 policy.py 的段边界状态机与官方客户端的兼容性未逐行核。
  • test xhard 的 demo 帧数分布未算，超 160 窗的局数要等 EVAL_ES_BOUND；drop_oldest 对成绩的影响无先例。
  • 52 格各 12 局、base 档各 12 局，样本小，只能看趋势。
