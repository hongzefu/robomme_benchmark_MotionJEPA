3.2 失败与缺条

任务性失败 attempt+1 换 seed（T10）、非任务性失败连续 3 次放弃记 exhausted、池崩溃产物 CRASHED_ 隔离——都沿用 1013。耗尽会让 metadata 出空洞，追加工具会整体拒绝；此时停在追加前把缺失清单交用户，不自动补 seed（P8）。

3.3 校验与追加

校验工具加 --layout test --tasks <组内任务> 后每组各跑 check（每格第一条，共 52 个样本）与 audit（全部身份）。追加逐组显式 --env；纯追加在 numstat 上每文件恰删 2 行（record_count 行与原末条的 }），判据按此写；追加后 ep≥50 的难度值是 xhard14 这类，所以任何消费方都必须用 <Task>XHard 建环境——评估侧正是这样做。

3.4 上传与读回校验

本机对 624 个 h5 流式算一次 sha256（校验工具不算 sha，约 0.3～0.4 TB 读盘），上传五组产物、清单与 SHA256SUMS 到新 bucket；HF_UPLOAD=PASS 后主会话在 GL 起 standard 分区纯 CPU job 流式读回比对，先 1 个对象冒烟。这两步是长尾，不阻塞交接。

四、评估侧机制（策略仓库分支）

4.1 一条链路评三个模型

评估是「模型进程 + 仿真进程」两进程：仿真进程按清单逐局用 seed 建环境，把画面与指令经 websocket 发给模型进程、收动作执行，直到终局（max_steps=2000 到顶记 timeout；成功与否取环境 info["status"]）。三个模型只换模型进程：你的两条 run 用本分支 scripts/training/serve_policy.py --policy.config=mme_vla_suite_b128_80k --policy.dir=<run>/60000（JAX；motion sidecar 是 torch 子进程；motion 开关由 run 目录里的 history_config.resolved.yaml 快照决定，所以下载必须带 run 级文件）；官方 79999 按 T18：同一份 serve_policy.py --policy.config=mme_vla_suite --policy.dir=v1-store/models/official-mme-vla/perceptual-framesamp-modul/79999（上次 eval-orig80k-modul-vs-official 的做法）。仿真进程只有一份：整份移植上次 GL 评估分支的 examples/robomme/（eval.py 走 --args.episode_plan：分片 JSON 的 groups 键是「任务/难度」→ episode 列表，另有 max_new_episodes、episode_wall_s、check_seed、try 包住的 make_env），改两处：load_plan 不再读候选库、改读 1200 局清单与 plan 的 groups；SpecEnvRunner 换成按难度分流建环境（<Task>XHard 或原任务名）并断言难度。两版客户端同源（共同祖先 ecf086c，openpi-client 零差异，websocket 的 reset／add_buffer／infer 字段未改），所以一份客户端能服务三个模型。每个单元在一个 srun --overlap --exact step 里同卡起模型进程与仿真进程（上次 GL 口径）。
