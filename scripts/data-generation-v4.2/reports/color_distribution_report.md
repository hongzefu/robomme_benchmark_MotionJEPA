# v4.2 颜色判决分布与分割过程走查报告

**一句话结论**：v4.2 的机械臂标定是「**逐像素查颜色表 → 四条形态学规则**」两段式，
两段各自的代价都能被量化，而且**第一段的代价有闭式**——由退化引理，颜色阶段判臂等价于
「该色只在臂列见过」，于是判臂颜色上的非臂像素**恒为 0**（精确率上界 1.000000 是恒等式
而不是经验数字），代价是召回上界被压到 **0.909211**，丢掉的 **9.0789%** 全落在 126 种
臂∩混合共享色上；四条形态学规则再把召回从 0.909211 压到留出集实测的 **0.818412**，
而误标物体像素在留出集上仍是 **0**。

产出于 2026-08-12，颜色表 `outputs/color_model.npz`（标定集 = benchmark val split
ep 0–9，160 episode 全帧；与 v4.1 的表逐位相同，已对拍）。

## 一、这份报告回答什么

`compare_gt.py` 与 `render_outputs.py` 给的是**最终指标**，看不出中间发生了什么。
另外两个入口把过程拆开画出来：

| 入口 | 产物 | 回答的问题 |
|---|---|---|
| `color_distribution.py` | `outputs/color_distribution/` | 颜色表把颜色空间切成了什么样？否决挡下了哪些颜色、代价多大？ |
| `segmentation_walkthrough.py` | `outputs/walkthrough/` | 拿一张真实帧，它是**一步一步**怎么被分出来的？某个像素**为什么**被判成这一类？ |

两个入口都**不碰 GT**（GT 只在走查图的「参照带」里当尺子），也都不改动既有链路——
`color_distribution.decide` 与 `segmentation_walkthrough.stagewise_masks` 分别与
`ColorModel.classify`、`arm_mask_v4.arm_masks_for_episode` 逐位对拍，对拍写死在
`tests/lightweight/test_color_distribution_v4_2.py` 里（12 个用例，0.34 秒）；走查脚本
内部还有一道运行期断言，逐阶段复算的最后一阶段与生产路径不一致就当场炸掉。

⚠ **与 v4.1 报告的口径差异**：v4.1 的同名报告有大量「veto vs noveto」对照，其中
**「③ 时间平滑会补像素」那条实证数的是 noveto 帧（13/16）**。v4.2 删掉了对照口径，
本报告的每一个数字都在**唯一口径**下重新测过，不沿用旧数（该条重测结果见第六节：**7/16**）。

## 二、颜色表本身

标定集 val ep0–9 全帧统计，**唯一颜色 16297 种**（ManiSkill 渲染确定性极强，24 位 RGB
本来就是天然离散量，所以用精确颜色而不是直方图 bin，一个超参都不需要）。

| 列 | 语义 | 像素数 | 支撑色数 |
|---|---|---:|---:|
| 列 0 | 纯背景 | 4,731,895,750 | 12,214 |
| 列 1 | 背景∪物体混合 | 4,846,769,500 | 14,627 |
| 列 2 | 机械臂 | 342,829,732 | 1,796 |

⚠ 三列是**重叠计数**：背景像素同时进列 0 与列 1，物体像素只进列 1，臂像素只进列 2。
所以「总像素数」是 `列 1 + 列 2 = 5,189,599,232`，**不能三列直接相加**（会把背景重复计
一遍）。本报告后面所有「像素量口径」都按这个定义加权。

关键的支撑交叠：**臂 ∩ 纯背景共享 0 色，臂 ∩ 混合共享 126 色，臂独有 1670 色**。
「臂与纯背景零共享」是整条链路能成立的结构性前提——臂的灰白只和**物体**撞色，不和桌面
背景撞色。

## 三、判决分布

![判决分布](../outputs/color_distribution/color_distribution.png)

九宫格版式：行 1 = 三类各一张「饱和度 × 亮度」散点（本链路最有分辨力的平面——机械臂是
低饱和的灰白壳体，任务物体大多带彩色，全部矛盾都挤在左上角那团灰白里）；行 2 = 三类
色板（等面积，按亮度排序）；行 3 = 像素量加权色带 / 亮度分布 / 判决似然平面。

| 类 | 色数 | 像素数 | 像素占比 |
|---|---:|---:|---:|
| 纯背景 | 12,214 | 4,731,895,750 | 91.18% |
| 背景∪物体混合 | 2,413 | 145,998,913 | 2.81% |
| 机械臂 | 1,670 | 311,704,569 | 6.01% |

**判臂颜色上的成分**：真实臂像素 311,704,569，真实非臂像素 **0**
⇒ 颜色阶段召回上界 **0.909211**、精确率上界 **1.000000**。

### 行 3 右「判决似然平面」是这条规则的几何形态

横轴 `log10 P(色|混合)`、纵轴 `log10 P(色|臂)`，混合列没见过的颜色 `P = 0`、log 取不到，
统一画进左侧那条「混合列从未见过」的专列。图上一眼可见：**判臂的点（大圆）全部落在那条
专列上，整个右半平面一个判臂点都没有**。这正是退化引理的图像形态——臂的裁决只看
「混合列见过没有」，与两个似然的具体数值无关。

## 四、否决的代价：126 种纯灰阶共享色

由退化引理的推论 2，颜色阶段丢掉的臂像素**恰好**是臂∩混合共享色上的臂像素，闭式如下：

| 项 | 值 |
|---|---:|
| 共享色数（臂列与混合列都见过） | **126** |
| 带走的臂像素 | **31,125,163** |
| 占全部臂像素 | **9.0789%** |
| 这 126 色上压着的非臂像素 | **53,143,358** |

`1 − 0.090789 = 0.909211`，与第三节的召回上界严丝合缝对上——**颜色阶段的全部损失就是
这一项，没有第二个来源**。

**126 种共享色的饱和度实测最大值为 0.000**，即**全部是 `R = G = B` 的纯灰阶**（126/126）。
带走臂像素最多的前几种：

| # | hex | RGB | 臂像素 | 混合像素 | 占全部臂像素 |
|---|---|---|---:|---:|---:|
| 1 | `#6C6C6C` | (108,108,108) | 10,257,480 | 2,376,817 | 2.992% |
| 2 | `#A8A8A8` | (168,168,168) | 5,515,849 | 4,791,004 | 1.609% |
| 3 | `#A9A9A9` | (169,169,169) | 4,315,546 | 2,421,952 | 1.259% |
| 4 | `#939393` | (147,147,147) | 1,441,725 | 8,502,084 | 0.421% |
| 5 | `#E7E7E7` | (231,231,231) | 726,323 | 29,972,309 | 0.212% |

前 3 种就占掉 **5.86** 个百分点，长尾极陡。语义很清楚：**灰白臂壳与灰白任务物体在
24 位 RGB 上完全同色**，形态学救不了（它们与臂连成一片、也触顶），只能在分类阶段用
支撑否决整批挡掉——这是刚性原则的直接价钱。

反过来看判臂的那 1670 色：**低饱和（< 0.1）的 470 种承担了 90.91% 的臂像素**，
高饱和的 1200 种只占 **0.0075%**（纯色数长尾，且混合列计数全为 0，从不进否决）。
也就是说，臂的像素质量几乎全压在灰白上，而灰白正是最容易与物体撞色的区段——
这条链路的全部张力就在这里。

## 五、召回与精确率的两段分解

把颜色阶段的上界与留出集（train ep10–19，160 episode / 77,272 帧全帧）实测放在一起，
四条形态学规则的代价就单独露出来了：

| 阶段 | 召回 | 精确率 | 误标物体像素 |
|---|---:|---:|---:|
| 颜色阶段上界（标定集 val ep0–9） | 0.909211 | 1.000000 | 0 |
| 留出集实测（形态学之后） | **0.818412** | **1.000000** | **0** |
| 形态学的相对损耗 | **−9.98%** | — | — |

读法：

1. **否决的代价在颜色阶段就定死了**：召回上界 0.909211，丢掉的 9.0789% 全是那 126 种
   纯灰阶共享色，形态学再怎么调都拿不回来。
2. **形态学再砍掉约一成召回**（−9.98%），主要来自「② 触顶连通域」与「④ 保守收缩 +
   腐蚀」——四条规则的方向刻意统一为「合起来只让标定区域变小或持平」。
3. **精确率两段都是 1.000000**：颜色阶段是恒等式（推论 1），形态学只删不加，所以传下去
   仍然是 1。留出集实测 `误标物体 0 / 误标背景 0 / 碰到物体的帧占比 0`。
4. **GT 兜底那部分也没出事**：留出集里 `setup` 快照未覆盖的 seg id 共 2,278,922 个像素
   （一律兜底归物体），其中被误标进机械臂的是 **0** 个。

⚠ 口径提醒：颜色阶段上界算在**标定集 val ep0–9**，留出集实测在 **train ep10–19**，两者
不是同一批帧，量级可比但不构成严格的逐位分解。跨集差异的另一个来源是留出集里 0.1866%
的像素颜色在标定集从未出现（`UNKNOWN`），一律按「不是机械臂」处理。

逐任务召回从 **0.684357**（StopCube）到 **0.851516**（MoveCube）。

## 六、分割过程逐格走查

每个任务一张（16 张，`outputs/walkthrough/<Task>_walkthrough.png`），取留出集
`episode_10`，帧号按「优先取误标物体最多的一帧；整段无误标则取 GT 臂像素最多的一帧」
——本轮 16 个任务的误标物体全为 0，因此全部走后一支。

![ButtonUnmask 走查](../outputs/walkthrough/ButtonUnmask_walkthrough.png)

一行七格：原图 → 颜色判决 → 候选 → ① 开运算 → ② 触顶连通域 → ③ 时间平滑 →
④ 保守收缩 + 腐蚀。**青色 = 该阶段保留的像素，红色 = 相对上一阶段被删掉的像素**，
脚注是像素数与**带符号**增量。底部参照带给 GT 三类真值、GT 臂、红遮罩产物与误差图。

ButtonUnmask ep10 第 222 帧的逐阶段像素数：

| 阶段 | 像素数 | 增量 |
|---|---:|---:|
| 候选：判臂像素 | 8,175 | — |
| ① 开运算 | 8,154 | −21 |
| ② 触顶连通域 | 7,925 | −229 |
| ③ 时间平滑 | 7,930 | **+5** |
| ④ 保守收缩 + 腐蚀 | **7,514** | −416 |
| 该帧误标物体 | **0** | |

读法：

- **候选阶段就已经很干净**：桌上那些白色按钮块的颜色在无臂场景里出现过，被支撑否决
  整批挡在候选之外，所以 ② 触顶连通域只需要删 229 px（那是零星的背景噪点连通块）；
- ③ 时间平滑在本帧**加了 5 px**（见下），它的常规作用是抹掉只闪一两帧的误判；
- ④ 保守收缩 + 腐蚀砍掉 416 px 的边缘，这是召回上界到实测那一成损耗的主要来源。

### ⚠ 顺带实证：③ 时间平滑真的会**补**像素（v4.2 口径重测）

走查图脚注带符号，于是这件事一眼可见：**16 个任务的走查帧里有 7 个，③ 时间平滑阶段的
像素数是上升的**——ButtonUnmask +5、InsertPeg +4、PatternLock +1、VideoPlaceButton +14、
VideoPlaceOrder +28、VideoRepick +3、VideoUnmaskSwap +1；其余 9 个持平或减少。
多数表决把「本帧不在候选、但前后帧在」的像素补了进来。

幅度最大的 VideoPlaceOrder ep10 第 102 帧：

| 阶段 | 像素数 | 增量 |
|---|---:|---:|
| 候选：判臂像素 | 16,636 | — |
| ① 开运算 | 16,621 | −15 |
| ② 触顶连通域 | 16,621 | ±0 |
| ③ 时间平滑 | **16,649** | **+28** |
| ④ 保守收缩 + 腐蚀 | **16,003** | −646 |

⚠ v4.1 报告里这条实证给的是 **13/16**，那数的是 **noveto** 帧；v4.2 唯一口径下重测是
**7/16**。数字变小很自然：否决把共享灰白整批挡在候选之外，候选本身更干净、更稳定，
前后帧之间可供「补」的差异也就更少。**结论不变，量级变了，所以必须重测而不是照抄。**

这正是 `arm_mask_v4.py` 里那条 ⚠ 的逐格证据：第 ④ 条**必须**写成「只保留**当前帧自己**
被判成机械臂的像素」这个白名单，而不是「扣掉物体」这个黑名单，否则这些补进来的像素会
留在产物里（v4 留出集实测抓到过 InsertPeg 的 292 个这样的误标像素，颜色在拟合表里压根
没出现过）。收紧之后，「整条链相对候选集单调收缩」这条设计原则才在**最终 mask** 上真正
成立——中间态可以短暂变大。`test_逐阶段单调收缩` 把这条边界写死：① ② ④ 逐步单调，
③ 不做单调断言，但最终 mask 必须是候选的子集。

## 七、逐像素举例：这个颜色为什么被判成这一类

每个任务一张（16 张，`outputs/walkthrough/<Task>_pixels.png`）：左边是标了点的放大原图，
右边一张表，逐点列出 24 位颜色、三列归一化似然 `P(色|背景) / P(色|混合) / P(色|臂)`、
判决、是否进入最终标定、GT 真身。

![BinFill 逐像素](../outputs/walkthrough/BinFill_pixels.png)

采样刻意不随机，而是把**两段代价与两段保护**各摆一个到台面上：

| 类别 | 说明 |
|---|---|
| 真臂 · 标到了 | 成功路径：混合列似然为 0，判臂，进最终标定 |
| 真臂 · 落在臂∩混合共享色 | **颜色阶段的漏标代价**：混合列似然 > 0 ⇒ 否决改判混合（纯支撑集判定，与似然大小无关） |
| 真臂 · 判臂但被形态学收掉 | **形态学阶段的漏标代价**：颜色阶段判臂，但被 ①②④ 之一删掉 |
| 真物体 · 判混合 | **红线是怎么守住的**：物体色在混合列见过，永远进不了臂 |
| 真臂 · 未见色 UNKNOWN | 标定集没见过的颜色，一律按「不是机械臂」处理 |
| 真背景 · 判纯背景 | 对照项 |

BinFill ep10 第 80 帧的表把两段代价并排摆着：第 3、4 行是 `#A8A8A8`(168,168,168) 与
`#6C6C6C`(108,108,108) 这两种**共享灰白**上的真臂像素，混合列似然分别是 9.885e-04 与
4.904e-04——都大于 0，于是被否决改判混合，最终标定列是红色的「否」；第 5、6 行是判臂
但被形态学收掉的真臂像素，混合列似然为 0、判决是「机械臂」，最终标定却仍是「否」。
**同样是漏标，成因完全不同**——这张表就是把这件事拆给人看。

## 九、已知口径与注意事项

1. **颜色阶段的两个「上界」算在标定集上**（val ep0–9），是**该颜色表在自己拟合集上**
   的天花板。形态学只会再往下砍，所以叫上界；跨到留出集还要额外承担 0.1866% 的未见色。
2. **像素量口径 = `counts[:, 混合] + counts[:, 臂]`**，不是三列相加（背景列与混合列是
   重叠计数）。报告里每张表都标了口径，别混着读。
3. **走查帧的选法**：优先取误标物体最多的一帧，全为 0 时取 GT 臂像素最多的一帧。
   本轮 16 个任务全部走后一支——这是刚性原则成立的副产物，不是选帧逻辑失效。
   前一支保留着，万一红线被击穿，走查图会自动切到出事的那一帧。
4. **精确率上界 = 1.000000 是恒等式**（退化引理推论 1），不是调参调出来的。
   `color_distribution.py` 每次跑完都会断言它，被破坏就 `SystemExit`——当自校验用。
5. **本报告的所有数字都在 v4.2 唯一口径下重新测过**，没有一个是从 v4.1 照抄的。
   v4.1 报告里带 noveto 对照的表与结论**不适用于 v4.2**，不要交叉引用。
