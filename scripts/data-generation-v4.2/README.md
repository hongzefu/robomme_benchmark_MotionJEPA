# 数据生成 v4.2：单一口径的机械臂标定（判别 = 纯支撑三段式）

本目录回答的问题与 [v4](../data-generation-v4/README.md) /
[v4.1](../data-generation-v4.1/README.md) 完全相同——**把 RoboMME `front_rgb` 里的机械臂
标出来、涂成纯红 (255,0,0)**——四条形态学规则一个字都没改，变的是判别侧：
**先删掉「不带否决」的对照口径，再把留下的那条规则改写成它的真实形态**。

| 方面 | v4.1 | **v4.2（本目录）** |

| 拟合侧 | —— | **逐字未变**，颜色表与 v4.1 逐位相同（已对拍） |

用户 2026-08-12 关键决策原话：

> 「生成 v4.2 只使用 veto 全规则完整的规则 不要再保留 no veto 产物重新生成 dataset

即：标定结果后续要对齐 Wan VAE 的编码网格（届时还会在网格层面进一步保守、降低采样），
两个变体并存会让网格对齐的口径复杂度翻倍，因此就此收敛到一条。

收敛之后追加的一步（同日）：在标定集上实测发现，留下的那条「归一化似然 argmax + 混合支撑

> 「这个机制是否不再需要 永远用只要一个颜色在混合列/背景列露过一次面（哪怕只有 1 个
> 像素），它就永远不可能被判成臂 这个逻辑」

（顺带一提：加不加「背景列」这个条件不影响任何结果——由 2.3 的重叠计数，背景列见过的

## 〇、刚性原则（第一判据，凌驾于其它一切指标）

> **不得把物体判错成 robot arm。「判错」以 ground truth 为准。**

精确说法：把整段 episode 每一帧最终被标定成机械臂的像素拿出来，逐个查它在 ground truth
（`obs/front_camera_segmentation` 经 `labels_from_segmentation` 得到的三类标签）里的真身，
**其中真身是「物体」的像素个数，累加起来必须恒等于 0**。这个数在各处指标里叫
`false_object_pixels`。

三件事必须一起成立，缺一条这条原则就是空话：

1. **判定口径偏保守，不偏宽松。** GT 侧的「物体」集合含**兜底项**：`setup/flow_objects`
   与 `setup/flow_excluded` 是 `reset()` 那一刻对 `segmentation_id_map` 的快照，
   **episode 运行中动态创建的 seg id 不在里面**（实测 5 个任务会出现：InsertPeg 箱顶
   插孔标记、PickHighlight 绿色高亮块、SwingXtimes 靶心圆盘、PatternLock 图案连线节点
   id 涨到 572、RouteStick 路线曲线涨到 710）。这些 id **一律兜底归物体**。也就是说
   凡认不出的东西都算物体，红线只会更严不会更松；这部分像素同时被 `uncovered_mask`
   单独计数，兜底不许静默。

2. **在标定集上它是恒等式，不是调出来的巧合。** 判臂的**定义**就是「混合列一次都没出现
   过」（见 2.4），而混合列已经把 GT 物体像素全部计入，所以判臂颜色在标定集上的物体像素
   **恰为 0**——这一步不需要任何引理，直接从定义读出来。评估集上唯一可能的漏洞是
   「标定集里只在臂上见过、评估集里却出现在物体上」的颜色（未见色走 `UNKNOWN` 不标，
   不构成误标来源）——**正是这一格必须逐次实测**。

3. **落成 fail-loud 硬闸门，且刻意不提供豁免开关。** `render_outputs.enforce_no_false_object`
   是唯一实现，被两个评估入口共用：
   - `render_outputs.py`（评估集 val ep10-19 全帧）**逐 episode** 校验；
   - `compare_gt.py`（评估集 val ep10）**逐任务**校验，GT 栏按构造恒为 0 不参与。

   非 0 时打印逐条明细并让 `main()` 返回 1（= 进程退出码非 0）。
   背景误标 `false_background_pixels` 继续记录但**不设闸门**——宗旨只针对物体。
   再加一道：`color_distribution.py` 跑完会断言「判臂颜色上的真实非臂像素 == 0」这个
   恒等式，被破坏就 `SystemExit`，用来兜住「颜色表或判别算式本身坏掉」的情形。

## 一、口径（用户逐条拍板，2026-08-12）

1. **标定集 = benchmark val split ep 0–9**（每任务 10 条，共 160 episode）。三套 split
   （`src/robomme/env_metadata/{train,val,test}/`）seed 固定；val 编码为
   `1_000_000 + task_index*10000 + ep*100 + retry`，每条 episode 的真实 seed 存在 h5 的
   `<episode>/setup/seed` 里（判 split 读它，不靠目录名猜）。
2. **GT 只允许提供两个场景级分布 + 臂分布**，不提供物体级逐像素分割（v4.1 起的削弱口径，
   现实语义 = 拿得到「没有臂的空场景」和「摆了物体但没有臂的场景」两种画面级监督，
   外加臂自己的外观样本）。
3. **判别规则 = 纯支撑三段式判据**（`N₀>0` 判背景 / `N₁=0 且 N₂>0` 判臂 / 其余判混合），
   无似然、无 argmax、无阈值、无开关。它是 v4.1 那条概率式规则的退化形态，实测三段逐位
   等价，见 2.5。
4. **评估集 = 同一个 val split 的 ep 10–19**（每任务 10 条，共 160 episode）：全帧指标走
   ep10-19，两栏对比图与走查图取其中的 ep10。与标定集**同 split、不同 episode**，
   seed 也因此不同（BinFill 标定 1040000–1040900 vs 评估 1041000–1041900），**零重叠**。
5. **标定与评估同住一份数据集** `artifacts/generated/v4seg-16env-val20ep`（`--split val
   --episodes 20`，320 episode）。⚠ 生成器的 `--episodes` 是「从 ep0 起的**数量**」不是
   区间，所以拿 ep10-19 只能连 ep0-19 一起生成；ep0-9 的 seed 固定，与旧的
   `v4seg-16env-val10ep` 逐位相同（已对拍），因此**颜色表不必重拟合**。
6. **产物目录名自带口径**：`validation_val_ep10-19` / `compare_gt_val_ep10` /
   `walkthrough_val_ep10` / `color_distribution_val_ep0-9`——`ls outputs/` 一眼看出每个
   数字算在哪批 episode 上，不用翻文档（用户 2026-08-12 决定：「所有的产物文件夹都写上
   at test/val ep几到几」）。

## 二、判别规则的精确流程

判别只问一件事：**这个像素的 24 位 RGB 颜色，在标定集里分别在哪几种像素上出现过、
各出现过多少次**。与画面内容、像素位置、邻居像素全都无关——所以判决可以脱离图片、
直接在颜色表上画出来（这正是 `color_distribution.py` 做的事）。

### 2.1 颜色怎么当键用

把每个像素的 R、G、B 三个字节拼成一个 24 位整数当查表的键：红占最高 8 位、绿居中、
蓝占最低 8 位。这个变换无损可逆，且天然可排序，查表用二分即可。

输入必须是「高 × 宽 × 3」且数据类型**恰好是 uint8**，否则直接报错——用浮点或别的位深
进来会静默改变键值，这种错必须当场炸掉而不是往下带。

用**精确颜色**而不是直方图 bin、也不拟合高斯，理由是它一个超参都不需要：ManiSkill 的
渲染确定性极强，颜色本身就是天然的离散量。改成 bin 就得回答「分多少个 bin」，改成高斯
就得回答「协方差怎么正则」，两个都是拍脑袋的量。

统计所用的标定集是 val split ep0–9 共 160 个 episode 的**全部帧的全部像素**。

### 2.2 GT 的 seg_id 怎么归成三类

`setup/flow_excluded` 与 `setup/flow_objects` 两张表是 seg_id 的枚举来源，按下面的规则
分成三类（`class_ids_from_setup`）：

| 类 | 收哪些 seg_id |
|---|---|
| **机械臂** | `flow_excluded` 里 `reason == "robot_link"` 的全部条目；外加 `flow_objects` 里 `kind == "tcp"` 的条目 |
| **背景** | `flow_excluded` 里 `reason == "background_prop"` 的全部条目（`table-workspace`、`ground`）；外加 seg_id 0 |
| **物体** | `flow_objects` 里除 `tcp` 之外的全部条目 |

三点补充：

- **seg_id 0** 表示这个像素没有命中任何几何体，归背景；
- **`kind == "tcp"`**（`panda_hand_tcp`）是夹爪的工具中心点，一个不参与渲染的虚拟坐标点，
  语义上属于机器人而不是任务物体，因此归**臂**。实测它的 seg_id 从来没在 segmentation
  图里出现过，这条分支是纯防御；
- 出现**未知的 `reason`** 直接抛错；三类集合两两不相交，由断言把关。

拿到三类集合后，`labels_from_segmentation` 把整张 segmentation 图翻译成三类标签图：
seg_id 落在臂集合里就是臂，落在背景集合里就是背景，**其余一律归物体**——这条兜底就是
第〇节说的「凡认不出的都算物体」，方向永远偏保守。

### 2.3 三列计数：为什么背景像素要记两遍

对**每一种颜色**记三个数字（`accumulate_frames`）：

| 列 | 含义 | 统计的是 |
|---|---|---|
| 列 0 | 纯背景 | 该颜色出现在 GT **背景**像素上的次数 |
| 列 1 | 背景∪物体混合 | 该颜色出现在 GT 背景**或** GT 物体像素上的次数 |
| 列 2 | 机械臂 | 该颜色出现在 GT **臂**像素上的次数 |

也就是说**背景像素同时被记进列 0 和列 1，物体像素只进列 1，臂像素只进列 2**——这就是
「重叠计数」。这么记不是随手为之，它换来两条后面全靠的性质：

1. **列 1 的计数逐色都不小于列 0**，因此**只要某颜色在列 1 里没出现过，它在列 0 里也
   一定没出现过**。这条是第 2.5 节那条引理的全部前提。
2. **列 1 与列 2 把每个像素恰好各记一次**，所以「总像素数 = 列 1 总量 + 列 2 总量」。
   三列直接相加会把背景像素重复计一遍，报告里所有「像素量口径」都按前者。

⚠ **不做「混合 − 背景」的减法**：两列逐色对减等于变相把物体分布还原出来，而本链路的
设定就是拿不到物体级监督。判别只被允许问「这一列见过没见过」。

### 2.4 一个像素是怎么被判的

对每个像素取它的颜色键，走两步（`ColorModel.classify`）：

**第 1 步 查表。** 在升序排列的颜色表里二分定位，**再验一次是否真的命中**（二分只给
插入位置，不验就会拿到邻居的计数）。没命中说明这个颜色在标定集里三列都没出现过，
直接标成 `UNKNOWN`，下游一律按「不是机械臂」处理。

**第 2 步 看三列各自见过没见过，按下表定类。** 只问「出现过 / 没出现过」，
**计数的数值大小完全不参与**：

| 判决 | 条件 | 读法 |
|---|---|---|
| 纯背景 | 列 0 大于 0 | 这个颜色在**没有物体也没有臂**的画面里出现过 |
| 机械臂 | 列 1 等于 0，且列 2 大于 0 | 在**任何无臂画面**里都没出现过，却在臂上出现过 |
| 混合 | 其余（等价于列 0 等于 0、列 1 大于 0） | 只在**摆了物体**的无臂画面里出现过 |

输出是一张与原图同尺寸的标签图，取值只有四种：未见色、纯背景、混合、机械臂。

三件事值得单独点出来：

- **三段互斥且穷尽。** 由 2.3 的性质 1，列 0 大于 0 就意味着列 1 也大于 0，跟判臂条件
  天然互斥；而表里每一行至少有一列大于 0（只收录真实出现过的颜色），所以不会漏。
  这两条前提由 `ColorModel.__post_init__` 的两道守卫 fail-loud 兜着——前提破了，规则会
  **静默判错**而不是报错，必须显式拦。
- **一个超参都没有。** 门限就是 0（出现过 / 没出现过），没有阈值、没有归一化、没有开关。
  也**不做「混合 − 背景」的减法**：两列逐色对减等于变相把物体分布还原出来，而本链路的
  设定就是拿不到物体级监督。
- **判臂那条是往保守方向倒的**，这正是刚性原则的落点：该颜色既然在无臂场景里出现过，
  就无法排除它属于物体。顺带一提，**臂列的存在是「未见色保守」能成立的前提**——如果只
  给两个场景级分布而没有臂的样本，臂就只能被定义成「没被其它类解释掉的颜色」，未见色
  反而会被迫判臂，失效方向与本链路的宗旨正好相反。

### 2.5 这条规则的来历：它是似然 argmax 的退化形态（实测三段全等价）

v4.1 / v4.2 前期的写法是个完整的概率式判别：每列除以本列像素总量得到 `P(颜色|类)`，
取 argmax（平手偏向非臂），再叠一条「凡混合列计数大于 0 一律改判混合」的否决。
2026-08-12 在标定集的 16297 个颜色上逐个核验，发现**三段判决全部退化成 2.4 那张表的
支撑判据，逐位一致**——那 145 亿个计数值一个都没进任何判决：

| 判决 | 旧写法 | 新写法 | 色数 | 实测 |
|---|---|---|---|---|
| 背景 | `P(c\|背景) > P(c\|混合)` 且胜过臂 | 列 0 大于 0 | 12214 | 逐位一致 |
| 混合 | argmax 取混合，或判臂后被否决 | 列 0 等于 0、列 1 大于 0 | 2413 | 逐位一致 |
| 机械臂 | argmax 取臂且未被否决 | 列 1 等于 0、列 2 大于 0 | 1670 | 逐位一致 |

于是把规则直接写成它的真实形态，删掉似然与 argmax。**两段的成因不同，必须分开记**：

- **判臂那一段是恒等式**，永远成立，与数据无关。证明分两个方向，各两句话：
  - **充分性**：设某颜色在混合列里没出现过。由 2.3 的性质 1，它在纯背景列里也一定没
    出现过，于是背景与混合两列的似然都是 0；而它在臂列里出现过就意味着臂的似然为正，
    argmax 必然选臂。又因为混合列计数为 0，否决条件不成立。所以判臂。
  - **必要性**：设某颜色最终判成了臂。否决没把它改判，说明混合列计数必须为 0；
    argmax 选中了臂，说明臂的似然为正，也就是臂列计数大于 0。两个条件都得到了。
- **背景 vs 混合那一段没有构造保证**，只是本批数据碰巧成立。旧口径下判背景的条件是
  `N₀/T₀ > N₁/T₁`，也就是**该颜色上的物体像素占比小于 `1 − T₀/T₁ = 2.37%`**
  （实测两列总量之比 `T₀/T₁ = 0.9762989`）；16297 个颜色里**没有一个**违反，所以两种
  写法在本批数据上逐位相同。**换一批数据可能就不同了**——但下游只消费「臂」，
  背景与混合的区分只用在出图上，不影响任何产物。

两条推论（现在都是定义的直接结果，不再需要引理）：

- **推论 1：红线在标定集上是恒等式。** 判臂要求混合列计数为 0，而混合列已经把 GT 物体
  像素全部计入，所以**这些颜色在标定集里的非臂像素恰好是 0**。于是「颜色阶段精确率
  上界 = 1.000」不是调出来的经验数字，是恒等式。代码照样把它算出来打印，是**当自校验
  用**——它不为 0 就说明颜色表或判别算式坏了，`color_distribution.py` 会直接退出。
- **推论 2：漏标代价有闭式。** 颜色阶段丢掉的臂像素，恰好是那些「臂列与混合列都出现过」
  的颜色（下称**共享色**）上的臂像素，一个不多一个不少。

**换规则的验收方式**：因为三段逐位等价，改写**不该改变任何产物数字**。实测结果见 6.2。

规则本身与「计数值零作用」由 `tests/lightweight/test_arm_mask_v4_2.py` 钉死，其中
`test_计数值大小不影响判决` 把整表计数放大到 10⁶ 倍、以及只放大单列，断言判决逐位不变
——旧的归一化似然写法通不过这一条（放大单列会改变列总量，进而改变似然的相对大小）。

## 三、四条形态学规则的精确流程

输入只有上一步的标签图，**完全不看 ground truth**。四条规则在**一个相位段之内**按顺序
执行；「候选像素」指的是这一帧里被判成机械臂的那些像素，它就是四条规则的输入。

### 3.1 两个贯穿全节的约定

**结构元**：腐蚀与膨胀都用同一个 **3×3 全 1 的方形窗口**，也就是**八邻域**（一个像素
加它周围一圈 8 个）。这个窗口固定不动，不作为可调项。

- **腐蚀**：只有当一个像素连同周围一圈 8 个邻居**全都**在前景里，它才留下；结果是整个
  区域向内缩一圈，孤立点直接消失。
- **膨胀**：每个前景像素把周围一圈也拉成前景；结果是整个区域向外涨一圈。

**边界**：OpenCV 做腐蚀时**把画面外当成前景**，所以贴着画面边缘的前景不会被边界削掉。
这条不是可有可无的细节——它直接影响第 ② 条「触到第 0 行」的判定。实测核验：把一块 3×3
的前景放在画面左上角腐蚀一次，左上角那两个像素仍然留着，说明上边界与左边界外侧确实被
当成了前景；若当成背景，整块贴边前景会被削掉一圈，② 的触顶判定随之改变。

### 3.2 四条规则

**① 开运算：先腐蚀一次，再膨胀一次。**
用途是去掉抗锯齿边缘与阴影上零星的臂色噪点：孤立的小点在腐蚀那一步就消失了，膨胀只能
把腐蚀后仍存活的臂身补回来，补不出新的东西。所以这一步的结果**一定是候选的子集**，
不会往物体那边长。

> ⚠ OpenCV 的 `iterations = n` 语义是「腐蚀 n 次再膨胀 n 次」，而不是做 n 次完整的开运算。
> 本链路 `n = 1`，两种理解等价，但改这个参数时要知道它是哪一种。

**② 只保留触到画面第 0 行的连通域。**
先按**八连通**把上一步的结果切成若干连通分量，然后**只保留那些至少有一个像素落在画面
第 0 行的分量**，其余整块删掉。

- 「触顶」的判定严格是**恰好第 0 行**，不是「前 N 行」，也不是「靠近顶部」；
- 保留是**整块保留**、删除是**整块删除**，不做部分裁剪；
- 输入为空、或者没有任何分量触顶时，结果就是空。

依据是场景的物理结构：机械臂根部固定在画面顶部、整条臂从上方伸进来，而桌面上的任务
物体不触顶。这是「不误标物体」最主要的**结构性**保障，比任何颜色阈值都硬。

**③ 3 帧滑动多数表决。**
对每一帧，看它自己和前后各一帧共 3 帧，某个像素在这 3 帧里**至少 2 帧**被 ② 保留下来，
本帧才保留它。判据统一表述为：**命中的帧数严格超过窗口帧数的一半**。

窗口在相位段的两端**自动截断、不补边**，于是逐情形是这样的：

| 情形 | 窗口帧数 | 要求 |
|---|---|---|
| 段长 ≥ 3 的内部帧 | 3 | 3 帧里至少 2 帧命中 |
| 段的首帧 / 末帧 | 2 | 2 帧**全中**（等价于取这两帧的交集） |
| 段长恰为 2 | 2 | 两帧输出都是这两帧的交集 |
| 段长恰为 1 | 1 | 原样不动 |

时间窗必须是**正奇数**，否则构造参数时就抛错。

⚠ **这是四条里唯一可能让区域变大的一条**：多数表决会把「本帧不在候选、但前后帧在」的
像素**补进来**。这不是 bug，是多数表决的定义使然——第 6.5 节有 3/16 个任务的实测证据。

**④ 保守收缩：先取白名单交，再腐蚀一次。**
先与**本帧自己的候选**取交集，也就是**只保留当前帧自己被判成机械臂的像素**；这一刀
同时扣掉判为混合的、判为背景的、以及未见色的像素，**哪怕它与臂连成一片**（接触帧的
典型情形）。然后整体腐蚀一次，削掉一圈边缘。顺序不能反：先交后腐蚀。

⚠ 这里写成**白名单**（「必须是本帧判定的臂」）而不是黑名单（「扣掉物体」）是**必须的**。
v4.1 留出集实测抓到过反例：③ 的多数表决把 InsertPeg 的 **292 个**像素补了进来，它们的
颜色（品红系 `(135,38,114)` 等）在拟合表里压根没出现过——黑名单拦不住这种像素，因为
它们既不是物体也不是背景，而是未见色。收紧成白名单之后，③ 就只能删不能加。

### 3.3 单调性：整条链单调，但不是每条都单调

> **命题.** 最终 mask 一定是本帧候选的子集。
>
> **理由.** ④ 的第一步就与本帧候选取交，结果不可能超出候选；第二步的腐蚀只会让它更小。
> 无论 ③ 之前补进来多少像素，都过不了这一关。

所以**整条链相对候选集是单调收缩的**，正对应本链路的宗旨——绝不误标物体，允许少量
机械臂没被标进去。但要注意这个说法的精确边界：

- **①②④ 逐条单调**：① 的结果含于候选，② 的结果含于 ① 的结果，④ 的结果含于它自己的输入；
- **③ 单独看不单调**，是 ④ 的白名单把它兜回来的；
- 因此「每一条规则都只会让标定区域变小或持平」这句话**对整条链成立、对 ①②④ 成立、
  但对 ③ 不成立**。走查图 `<Task>_walkthrough.png` 每格脚注的**带符号**增量把这件事画了
  出来（③ 那格出现 `+n` 就是它在补像素），`walkthrough.json` 里的 `该帧时间平滑增量`
  字段是同一件事的机读版本。

### 3.4 相位切段

`info/is_video_demo` 标出的两个相位之间场景会重摆，跨相位做时间平滑等于把两个不同场景
的帧混在一起投票。因此先按这个标记的**极大等值连续段**把整段 episode 切开，每段独立跑
①–④，段与段之间互不影响。两处 fail-loud：帧数与相位标记数对不上时抛错，切段没能覆盖
全部帧时抛错。

### 3.5 输出

把最终 mask 里的像素涂成纯红 `(255, 0, 0)`，其余像素与原图**逐位相同**。涂色写在副本上，
不改输入数组。

### 3.6 三个可调项

只有三个整数，且都是形态学的最小配置：开运算 1 次、时间窗 3 帧、最终腐蚀 1 次。
**它们不是「阈值」**——没有任何一个是在某个连续量上切一刀，调大调小只改变收缩的力度，
不改变判据本身。整条链路的**浮点阈值数量为 0**。

## 五、用法

```bash
# 1.（一般不用跑）生成 val split 数据集：ep0-9 当标定集、ep10-19 当评估集
#    ⚠ 正式生成前须与用户确认新的 --output-dir 名字（必须是不存在或空的目录）

uv run --locked scripts/data-generation-v4.2/generate_dataset.py \
  --output-dir artifacts/generated/v4seg-16env-val20ep --env all --episodes 20 \
  --workers 16 --gpus 0,1 --split val \

uv run --no-sync python scripts/data-generation-v4.2/fit_color_model.py \
  --h5 'artifacts/generated/v4seg-16env-val20ep/record_dataset_*.h5' \
  --episodes 0-9 --out scripts/data-generation-v4.2/outputs/color_model.npz

# 3. 评估集全帧指标 + preview（val ep10-19，160 episode，含刚性闸门）
#    下面四条的 --h5 / --episode(s) / --out 都已是默认值，日常直接裸跑即可
uv run --no-sync python scripts/data-generation-v4.2/render_outputs.py --workers 16

# 4. 两栏对比出图（预测 | GT，val ep10，16 张 + metrics.json，含刚性闸门）
uv run --no-sync python scripts/data-generation-v4.2/compare_gt.py --workers 16

# 5. 颜色判决分布出图（四面板一张图 + stats.json；只读颜色表，不碰 h5）
uv run --no-sync python scripts/data-generation-v4.2/color_distribution.py

# 6. 分割过程走查出图（16 任务 × 评估集 ep10，每任务一张）
uv run --no-sync python scripts/data-generation-v4.2/segmentation_walkthrough.py --workers 16

# 7. 单元测试（v4 / v4.1 / v4.2 三套一起跑，互不污染）
uv run --no-sync python -m pytest tests/lightweight/test_arm_mask_v4.py \
  tests/lightweight/test_arm_mask_v4_1.py tests/lightweight/test_color_distribution.py \
  tests/lightweight/test_arm_mask_v4_2.py tests/lightweight/test_color_distribution_v4_2.py -q
```

## 六、实测结论（2026-08-12，全部来自 v4.2 自己重新生成的产物）

### 6.1 颜色表与 v4.1 逐位相同（拟合口径逐字未变）

重新在 val ep0–9 全帧上拟合，单进程 **1140.1 秒**，**唯一颜色 16297 种**，npz 108 KB。
与 `../data-generation-v4.1/outputs/color_model.npz` 对拍：`schema_version`、`colors`、
`counts` **三项全部逐位相等**。v4.2 只改推理侧，拟合侧一个字没动，这条对拍把它坐实。

| 列 | 语义 | 像素数 | 支撑色数 |
|---|---|---:|---:|
| 列 0 | 纯背景 | 4,731,895,750 | 12,214 |
| 列 1 | 背景∪物体混合 | 4,846,769,500 | 14,627 |
| 列 2 | 机械臂 | 342,829,732 | 1,796 |

支撑交叠：**臂 ∩ 纯背景 = 0 色**，**臂 ∩ 混合 = 126 色**，臂独有 1670 色。
「臂与纯背景零共享」是整条链路能成立的结构性前提——臂的灰白只和**物体**撞色，
不和桌面背景撞色。

### 6.2 三段退化的实测核验，以及「换规则没换语义」的字节级证据

**（a）三段判决逐位等价**（16297 色逐个核验）：

| 判决 | 旧写法（似然 argmax + 否决） | 新写法（纯支撑） | 是否逐位一致 |
|---|---:|---:|---|
| 纯背景 | 12214 色 | 12214 色 | **是** |
| 混合 | 2413 色 | 2413 色 | **是** |
| 机械臂 | 1670 色 | 1670 色 | **是** |

`1796 种臂列出现过的颜色 − 126 种共享色 = 1670`，与判臂色数严丝合缝。
另外核验了两条结构前提：`supp(N₀) ⊆ supp(N₁)` 与 `N₁ ≥ N₀` **逐元素成立**。

**（b）改规则后重跑四个入口，产物数字一个都没变**——这是判别规则改写那一轮最强的验收。

⚠ 这组对比做在**当时的评估集（train ep10-19）**上，之后评估集才整体搬到 val ep10-19，
所以下表的 77,272 帧与 6.3 的 78,764 帧不是同一批；对比结论（换规则不改数字）不受影响。

| 产物 | 与改规则前的 diff |
|---|---|
| `metrics.json`（当时 160 ep / 77,272 帧） | **只有 `参数.判别规则` 字符串与 `耗时秒` 两行**，全部指标逐位相同 |
| 16 张 preview | **逐字节相同**（git 认为未修改） |
| 两栏对比的 `metrics.json` | 同上，只有规则字符串与耗时 |
| `stats.json` | **逐字节相同** |
| `walkthrough.json` | 去掉已取消的 `逐像素举例` 字段后，逐任务数字逐位相同 |

两栏对比图与走查图确有变化，但只因为图上印的**文案**改了（列标题改口径名、走查图新增
底部规则说明带），mask 本身没动——由上表的 metrics 佐证。

**（c）判臂色的成分**（推论 1、2 的实测）：

| 项 | 值 |
|---|---:|
| 判臂颜色上的真实臂像素 | 311,704,569 |
| **判臂颜色上的真实非臂像素** | **0**（推论 1，恒等式） |
| 颜色阶段召回上界 | 0.909211 |
| 颜色阶段精确率上界 | **1.000000** |

规则代价（推论 2 的闭式，纯支撑集口径）：**126 种**臂∩混合共享色带走
**31,125,163** 个臂像素 = 全部臂像素的 **9.0789%**（`1 − 0.090789 = 0.909211`，与召回
上界严丝合缝对上）；同时这 126 色上压着 **53,143,358** 个非臂像素——这就是它们必须被
挡下的理由。这 126 色实测**全部是 `R=G=B` 的中性灰白**（饱和度最大 0.000），
单个最重的 `#6C6C6C` 一个色就吃掉 2.99% 的臂像素。

### 6.3 评估集全帧（val ep10–19，160 episode / 78,764 帧）

| 指标 | 值 |
|---|---:|
| **误标物体像素（刚性红线）** | **0** |
| 误标背景像素 | **0** |
| **标定精确率** | **1.000000** |
| 机械臂召回 | **0.817440** |

| 未见颜色占比 | 0.1914% |
| GT 兜底（setup 未覆盖 seg id）像素 | 2,267,011，其中被误标进机械臂 **0** |
| GT 臂像素 / 标定像素 | 341,842,908 / 279,436,234 |
| GT 物体像素（红线的分母） | 122,842,049，误标 **0** |

逐任务召回从 **0.672621**（StopCube）到 **0.851839**（MoveCube）。
闸门输出：`刚性红线通过：评估集（val ep10-19）逐 episode 共 160 项，GT 判定的误标物体

⚠ **与旧的 train ep10-19 口径对照**（评估集搬家前后）：召回 0.818412 → **0.817440**、
未见色 0.1866% → **0.1914%**，误标物体与精确率两项都不变（0 / 1.000000）。差别很小是
预期的——同一张颜色表、同一套规则，换的只是被评的那批 episode。⚠ 但**这两组数不是同一
批帧，不能当成「性能下降了 0.001」来读**。

### 6.4 val ep10 两栏对比（16 张 + metrics.json）

**16/16 任务误标物体 = 0**，GT 栏自校验误标也全为 0（出图链路自身没走样）。
逐任务召回 0.699032（StopCube）～ 0.857557（InsertPeg）。耗时 8.4 秒。

### 6.5 分割过程走查（评估集 val ep10，16 张）

16 个任务全部 `该帧误标物体 0 px`；逐阶段复算与 `arm_masks_for_episode` 的运行期
逐位断言全部通过。

**③ 时间平滑在 3/16 个任务的走查帧上「补」了像素**（VideoRepick +10、ButtonUnmaskSwap +5、
SwingXtimes +3），其余 13 个持平或减少。这是 §3.3「③ 单独看不单调」的直接实证。
幅度最大的 VideoRepick val ep10 第 95 帧：

| 阶段 | 像素数 | 增量 |
|---|---:|---:|
| 候选：判臂像素 | 11,346 | — |
| ① 开运算 | 11,338 | −8 |
| ② 触顶连通域 | 11,338 | ±0 |
| ③ 时间平滑 | **11,348** | **+10** ← 多数表决在补像素 |
| ④ 保守收缩 + 腐蚀 | **10,785** | −563 |

④ 的白名单交把 ③ 补进来的那 10 个像素连同边缘一起收掉，最终 mask 仍是候选的子集。

⚠ 「几分之几的任务上 ③ 在补像素」这个数**逐评估集重测、不许照抄**：v4.1 的 noveto 口径
数出 13/16、train ep10 数出 7/16、本轮 val ep10 数出 **3/16**。走查每个任务只取一帧，
这个比例本来就带很强的抽样噪声——它证明的是「③ 确实会补」这件定性事实，不是一个稳定指标。

## 七、已知代价（诚实清单）

1. **臂与混合共享的颜色被规则全部挡下**：灰白臂壳与灰白任务物体同色的部分照旧漏标。
   这是刚性原则的直接价钱，且由推论 2 可精确写出闭式，不是模糊的「大概损失一些」。
2. **物体误标在评估集上没有理论零保证**：标定集上是恒等式（推论 1），评估集上依赖
   「拟合集的颜色支撑覆盖得够全」。所以才有硬闸门——数字以每次实测为准，不以推理为准。
3. **未见颜色一律不标**：标定集（val ep0-9）没见过的颜色在评估集出现时按「不是机械臂」
   处理。方向与宗旨一致（宁可漏标）。
4. **触顶规则漏掉非从上方入画的臂**（沿用 v4 口径，属可接受漏标）。
5. **③ 时间平滑单独看不单调**：整条链的单调性靠 ④ 的白名单兜住（6.5 节实测 3/16 个
   走查帧上 ③ 在补像素）。改动 ④ 时务必记得这点。
