## 〇、刚性原则（第一判据，凌驾于其它一切指标）

> **不得把物体判错成 robot arm。「判错」以 ground truth 为准。**

精确说法：把整段 episode 每一帧最终被标定成机械臂的像素拿出来，逐个查它在 ground truth
（`obs/front_camera_segmentation` 经 `labels_from_segmentation` 得到的三类标签）里的真身，
**其中真身是「物体」的像素个数，累加起来必须恒等于 0**。这个数在各处指标里叫
`false_object_pixels`。

三件事必须一起成立，缺一条这条原则就是空话：

1. **判定口径偏保守，不偏宽松。** GT 侧的「物体」集合含**兜底项**：`setup/flow_objects`
   与 `setup/flow_excluded` 是 `reset()` 那一刻对 `segmentation_id_map` 的快照，
   **episode 运行中动态创建的 seg id 不在里面**（实测 5 个任务会出现：InsertPeg 箱顶
   插孔标记、PickHighlight 绿色高亮块、SwingXtimes 靶心圆盘、PatternLock 图案连线节点
   id 涨到 572、RouteStick 路线曲线涨到 710）。这些 id **一律兜底归物体**。也就是说
   凡认不出的东西都算物体，红线只会更严不会更松；这部分像素同时被 `uncovered_mask`
   单独计数，兜底不许静默。

2. **在拟合集上它是恒等式，不是调出来的巧合。** 由下面 2.5 节的退化引理，被判成机械臂的
   颜色**在混合列里一次都没出现过**，而混合列已经把 GT 物体像素全部计入，所以判臂颜色
   在拟合集上的物体像素**恰为 0**。评估集上唯一可能的漏洞是「拟合集里只在臂上见过、
   评估集里却出现在物体上」的颜色（未见色走 `UNKNOWN` 不标，不构成误标来源）
   ——**正是这一格必须逐次实测**。

3. **落成 fail-loud 硬闸门，且刻意不提供豁免开关。** `render_outputs.enforce_no_false_object`
   是唯一实现，被两个评估入口共用：
   - `render_outputs.py`（留出集 train ep10-19 全帧）**逐 episode** 校验；
   - `compare_gt.py`（train ep0）**逐任务**校验，GT 栏按构造恒为 0 不参与。

   非 0 时打印逐条明细并让 `main()` 返回 1（= 进程退出码非 0）。
   背景误标 `false_background_pixels` 继续记录但**不设闸门**——宗旨只针对物体。
   再加一道：`color_distribution.py` 跑完会断言「判臂颜色上的真实非臂像素 == 0」这个
   恒等式，被破坏就 `SystemExit`，用来兜住「颜色表或判别算式本身坏掉」的情形。

## 一、口径（用户逐条拍板，2026-08-12）

1. **标定集 = benchmark val split ep 0–9**（每任务 10 条，共 160 episode）。三套 split
   （`src/robomme/env_metadata/{train,val,test}/`）seed 固定；val 编码为
   `1_000_000 + task_index*10000 + ep*100 + retry`。标定数据集
   `artifacts/generated/v4seg-16env-val10ep` 由本目录 `generate_dataset.py --split val`
   生成，**v4.2 不重造数据集**，直接复用。
2. **GT 只允许提供两个场景级分布 + 臂分布**，不提供物体级逐像素分割（v4.1 起的削弱口径，
   现实语义 = 拿得到「没有臂的空场景」和「摆了物体但没有臂的场景」两种画面级监督，
   外加臂自己的外观样本）。
3. **判别规则 = 归一化似然 argmax + 混合支撑否决**，两步都是规则的固有组成部分，无开关。
4. **评估集**：train split ep 0（两栏对比图与走查图）、train split ep 10–19（留出集全帧
   指标）。两者都与标定集零重叠。

## 二、判别规则的精确流程

判别只问一件事：**这个像素的 24 位 RGB 颜色，在标定集里分别在哪几种像素上出现过、
各出现过多少次**。与画面内容、像素位置、邻居像素全都无关——所以判决可以脱离图片、
直接在颜色表上画出来（这正是 `color_distribution.py` 做的事）。

### 2.1 颜色怎么当键用

把每个像素的 R、G、B 三个字节拼成一个 24 位整数当查表的键：红占最高 8 位、绿居中、
蓝占最低 8 位。这个变换无损可逆，且天然可排序，查表用二分即可。

输入必须是「高 × 宽 × 3」且数据类型**恰好是 uint8**，否则直接报错——用浮点或别的位深
进来会静默改变键值，这种错必须当场炸掉而不是往下带。

用**精确颜色**而不是直方图 bin、也不拟合高斯，理由是它一个超参都不需要：ManiSkill 的
渲染确定性极强，颜色本身就是天然的离散量。改成 bin 就得回答「分多少个 bin」，改成高斯
就得回答「协方差怎么正则」，两个都是拍脑袋的量。

统计所用的标定集是 val split ep0–9 共 160 个 episode 的**全部帧的全部像素**。

### 2.2 GT 的 seg_id 怎么归成三类

`setup/flow_excluded` 与 `setup/flow_objects` 两张表是 seg_id 的枚举来源，按下面的规则
分成三类（`class_ids_from_setup`）：

| 类 | 收哪些 seg_id |
|---|---|
| **机械臂** | `flow_excluded` 里 `reason == "robot_link"` 的全部条目；外加 `flow_objects` 里 `kind == "tcp"` 的条目 |
| **背景** | `flow_excluded` 里 `reason == "background_prop"` 的全部条目（`table-workspace`、`ground`）；外加 seg_id 0 |
| **物体** | `flow_objects` 里除 `tcp` 之外的全部条目 |

三点补充：

- **seg_id 0** 表示这个像素没有命中任何几何体，归背景；
- **`kind == "tcp"`**（`panda_hand_tcp`）是夹爪的工具中心点，一个不参与渲染的虚拟坐标点，
  语义上属于机器人而不是任务物体，因此归**臂**。实测它的 seg_id 从来没在 segmentation
  图里出现过，这条分支是纯防御；
- 出现**未知的 `reason`** 直接抛错；三类集合两两不相交，由断言把关。

拿到三类集合后，`labels_from_segmentation` 把整张 segmentation 图翻译成三类标签图：
seg_id 落在臂集合里就是臂，落在背景集合里就是背景，**其余一律归物体**——这条兜底就是
第〇节说的「凡认不出的都算物体」，方向永远偏保守。

### 2.3 三列计数：为什么背景像素要记两遍

对**每一种颜色**记三个数字（`accumulate_frames`）：

| 列 | 含义 | 统计的是 |
|---|---|---|
| 列 0 | 纯背景 | 该颜色出现在 GT **背景**像素上的次数 |
| 列 1 | 背景∪物体混合 | 该颜色出现在 GT 背景**或** GT 物体像素上的次数 |
| 列 2 | 机械臂 | 该颜色出现在 GT **臂**像素上的次数 |

也就是说**背景像素同时被记进列 0 和列 1，物体像素只进列 1，臂像素只进列 2**——这就是
「重叠计数」。这么记不是随手为之，它换来两条后面全靠的性质：

1. **列 1 的计数逐色都不小于列 0**，因此**只要某颜色在列 1 里没出现过，它在列 0 里也
   一定没出现过**。这条是第 2.5 节那条引理的全部前提。
2. **列 1 与列 2 把每个像素恰好各记一次**，所以「总像素数 = 列 1 总量 + 列 2 总量」。
   三列直接相加会把背景像素重复计一遍，报告里所有「像素量口径」都按前者。

⚠ **不做「混合 − 背景」的减法**：两列逐色对减等于变相把物体分布还原出来，而本链路的
设定就是拿不到物体级监督。归一化似然是不动用类先验时唯一诚实的比较方式。

### 2.4 一个像素是怎么被判的

对每个像素取它的颜色键，按顺序走四步（`ColorModel.classify`）：

**第 1 步 查表。** 在升序排列的颜色表里二分定位，**再验一次是否真的命中**（二分只给
插入位置，不验就会拿到邻居的计数）。没命中说明这个颜色在标定集里三列都没出现过。

**第 2 步 比归一化似然，取最大的一类。** 每一列先各自除以**本列的像素总量**，得到
「在这一类里，这种颜色出现的频率」，再取三者中最大的那一类。

- 除以本列总量这一步是关键：它把「这一类总共有多少像素」这个**类先验**除掉了。
  混合列里物体占多大比重是未知的，任何直接拿原始计数比大小的规则都在偷用先验。
- **平手时一律偏向非臂**：实现取的是第一个最大值，而三列顺序恰好是（背景，混合，臂），
  所以判臂必须**严格**胜出，打平判不了臂。
- 若某一列的总量为 0，归一化没有意义，直接抛错，不静默除零。

**第 3 步 混合支撑否决。** 上一步若判成了臂，再检查一次：**这种颜色只要在混合列里
出现过（计数大于 0），就一律改判混合**。门限就是「出现过 / 没出现过」，也就是 0，
不引入任何新阈值。理由是那条刚性原则：该颜色既然在无臂场景里出现过，就无法排除它属于
物体，只能往保守方向倒。

**第 4 步 没见过的颜色一律置 UNKNOWN。** 第 1 步没命中的像素，最后统一标成 `UNKNOWN`，
下游一律按「不是机械臂」处理。

输出是一张与原图同尺寸的标签图，取值只有四种：未见色、纯背景、混合、机械臂。

> 顺带一提，**臂列的存在是「未见色保守」能成立的前提**：如果只给两个场景级分布而没有
> 臂的样本，臂就只能被定义成「没被其它类解释掉的颜色」，未见色反而会被迫判臂——失效
> 方向与本链路的宗旨正好相反。

### 2.5 退化引理：似然的数值根本不进臂的裁决

前面两步看起来是个完整的概率式判别，但**在否决全开的口径下它会退化**：

> **引理.** 一种颜色最终被判成机械臂，**当且仅当**它满足两个条件：
> **在混合列里一次都没出现过，且在臂列里至少出现过一次**。
> 两个似然的具体数值完全不参与这个判定。

**证明**分两个方向，都只有两句话：

- **充分性**：设某颜色在混合列里没出现过。由 2.3 的性质 1，它在纯背景列里也一定没出现过，
  于是背景与混合两列的似然都是 0；而它在臂列里出现过就意味着臂的似然为正，第 2 步必然
  选臂。又因为混合列计数为 0，第 3 步的否决条件不成立，不改判。所以判臂。
- **必要性**：设某颜色最终判成了臂。第 3 步没把它改判，说明它的混合列计数必须为 0；
  第 2 步选中了臂，说明臂的似然为正，也就是臂列计数大于 0。两个条件都得到了。

三条推论，都是 v4.2 判读的基石：

- **推论 1：红线在拟合集上是恒等式。** 判臂的颜色混合列计数恒为 0，而混合列已经把 GT
  物体像素全部计入，所以**这些颜色在标定集里的非臂像素恰好是 0**。于是「颜色阶段精确率
  上界 = 1.000」不是调出来的经验数字，是恒等式。代码照样把它算出来打印，是**当自校验
  用**——它不为 0 就说明颜色表或判别算式坏了，`color_distribution.py` 会直接退出。
- **推论 2：漏标代价有闭式。** 颜色阶段丢掉的臂像素，恰好是那些「臂列与混合列都出现过」
  的颜色（下称**共享色**）上的臂像素，一个不多一个不少。这是**纯支撑集**的表述——只问
  「出现过没有」，不需要任何似然计算，也不需要「未否决的 argmax」。
- **推论 3：似然只管一个下游不看的区分。** 似然大小与类先验只影响「背景 vs 混合」怎么分，
  而下游只关心「是不是臂」。这正是「把监督从 v4 的三类分割削弱成两分布 + 臂几乎零代价」
  的机理——v4.1 观察到了这个现象，这里给出了它的原因。

⚠ 代码**仍保留完整的两步**（先比似然再否决），不按引理化简成一句支撑集判断。规则要写成
它的完整形态，而不是写成它碰巧退化成的样子；等价性交给
`tests/lightweight/test_arm_mask_v4_2.py::test_判臂等价于纯支撑判据` 钉死。

实测核验（本目录 `outputs/color_model.npz`，16297 色）：完整流程判臂 **1670** 色，
按引理的支撑集条件判臂也是 **1670** 色，两者**逐位一致**；且 1796 种臂列出现过的颜色
减去 126 种共享色，正好等于 1670。

## 三、四条形态学规则的精确流程

输入只有上一步的标签图，**完全不看 ground truth**。四条规则在**一个相位段之内**按顺序
执行；「候选像素」指的是这一帧里被判成机械臂的那些像素，它就是四条规则的输入。

### 3.1 两个贯穿全节的约定

**结构元**：腐蚀与膨胀都用同一个 **3×3 全 1 的方形窗口**，也就是**八邻域**（一个像素
加它周围一圈 8 个）。这个窗口固定不动，不作为可调项。

- **腐蚀**：只有当一个像素连同周围一圈 8 个邻居**全都**在前景里，它才留下；结果是整个
  区域向内缩一圈，孤立点直接消失。
- **膨胀**：每个前景像素把周围一圈也拉成前景；结果是整个区域向外涨一圈。

**边界**：OpenCV 做腐蚀时**把画面外当成前景**，所以贴着画面边缘的前景不会被边界削掉。
这条不是可有可无的细节——它直接影响第 ② 条「触到第 0 行」的判定。实测核验：把一块 3×3
的前景放在画面左上角腐蚀一次，左上角那两个像素仍然留着，说明上边界与左边界外侧确实被
当成了前景；若当成背景，整块贴边前景会被削掉一圈，② 的触顶判定随之改变。

### 3.2 四条规则

**① 开运算：先腐蚀一次，再膨胀一次。**
用途是去掉抗锯齿边缘与阴影上零星的臂色噪点：孤立的小点在腐蚀那一步就消失了，膨胀只能
把腐蚀后仍存活的臂身补回来，补不出新的东西。所以这一步的结果**一定是候选的子集**，
不会往物体那边长。

> ⚠ OpenCV 的 `iterations = n` 语义是「腐蚀 n 次再膨胀 n 次」，而不是做 n 次完整的开运算。
> 本链路 `n = 1`，两种理解等价，但改这个参数时要知道它是哪一种。

**② 只保留触到画面第 0 行的连通域。**
先按**八连通**把上一步的结果切成若干连通分量，然后**只保留那些至少有一个像素落在画面
第 0 行的分量**，其余整块删掉。

- 「触顶」的判定严格是**恰好第 0 行**，不是「前 N 行」，也不是「靠近顶部」；
- 保留是**整块保留**、删除是**整块删除**，不做部分裁剪；
- 输入为空、或者没有任何分量触顶时，结果就是空。

依据是场景的物理结构：机械臂根部固定在画面顶部、整条臂从上方伸进来，而桌面上的任务
物体不触顶。这是「不误标物体」最主要的**结构性**保障，比任何颜色阈值都硬。

**③ 3 帧滑动多数表决。**
对每一帧，看它自己和前后各一帧共 3 帧，某个像素在这 3 帧里**至少 2 帧**被 ② 保留下来，
本帧才保留它。判据统一表述为：**命中的帧数严格超过窗口帧数的一半**。

窗口在相位段的两端**自动截断、不补边**，于是逐情形是这样的：

| 情形 | 窗口帧数 | 要求 |
|---|---|---|
| 段长 ≥ 3 的内部帧 | 3 | 3 帧里至少 2 帧命中 |
| 段的首帧 / 末帧 | 2 | 2 帧**全中**（等价于取这两帧的交集） |
| 段长恰为 2 | 2 | 两帧输出都是这两帧的交集 |
| 段长恰为 1 | 1 | 原样不动 |

时间窗必须是**正奇数**，否则构造参数时就抛错。

⚠ **这是四条里唯一可能让区域变大的一条**：多数表决会把「本帧不在候选、但前后帧在」的
像素**补进来**。这不是 bug，是多数表决的定义使然——第 6.5 节有 7/16 个任务的实测证据。

**④ 保守收缩：先取白名单交，再腐蚀一次。**
先与**本帧自己的候选**取交集，也就是**只保留当前帧自己被判成机械臂的像素**；这一刀
同时扣掉判为混合的、判为背景的、以及未见色的像素，**哪怕它与臂连成一片**（接触帧的
典型情形）。然后整体腐蚀一次，削掉一圈边缘。顺序不能反：先交后腐蚀。

⚠ 这里写成**白名单**（「必须是本帧判定的臂」）而不是黑名单（「扣掉物体」）是**必须的**。
v4.1 留出集实测抓到过反例：③ 的多数表决把 InsertPeg 的 **292 个**像素补了进来，它们的
颜色（品红系 `(135,38,114)` 等）在拟合表里压根没出现过——黑名单拦不住这种像素，因为
它们既不是物体也不是背景，而是未见色。收紧成白名单之后，③ 就只能删不能加。

### 3.3 单调性：整条链单调，但不是每条都单调

> **命题.** 最终 mask 一定是本帧候选的子集。
>
> **理由.** ④ 的第一步就与本帧候选取交，结果不可能超出候选；第二步的腐蚀只会让它更小。
> 无论 ③ 之前补进来多少像素，都过不了这一关。

所以**整条链相对候选集是单调收缩的**，正对应本链路的宗旨——绝不误标物体，允许少量
机械臂没被标进去。但要注意这个说法的精确边界：

- **①②④ 逐条单调**：① 的结果含于候选，② 的结果含于 ① 的结果，④ 的结果含于它自己的输入；
- **③ 单独看不单调**，是 ④ 的白名单把它兜回来的；
- 因此「每一条规则都只会让标定区域变小或持平」这句话**对整条链成立、对 ①②④ 成立、
  但对 ③ 不成立**。走查图 `<Task>_walkthrough.png` 每格脚注的**带符号**增量把这件事画了
  出来（③ 那格出现 `+n` 就是它在补像素），`walkthrough.json` 里的 `该帧时间平滑增量`
  字段是同一件事的机读版本。

### 3.4 相位切段

`info/is_video_demo` 标出的两个相位之间场景会重摆，跨相位做时间平滑等于把两个不同场景
的帧混在一起投票。因此先按这个标记的**极大等值连续段**把整段 episode 切开，每段独立跑
①–④，段与段之间互不影响。两处 fail-loud：帧数与相位标记数对不上时抛错，切段没能覆盖
全部帧时抛错。

### 3.5 输出

把最终 mask 里的像素涂成纯红 `(255, 0, 0)`，其余像素与原图**逐位相同**。涂色写在副本上，
不改输入数组。

### 3.6 三个可调项

只有三个整数，且都是形态学的最小配置：开运算 1 次、时间窗 3 帧、最终腐蚀 1 次。
**它们不是「阈值」**——没有任何一个是在某个连续量上切一刀，调大调小只改变收缩的力度，
不改变判据本身。整条链路的**浮点阈值数量为 0**。

## 五、用法

```bash
# 1.（一般不用跑）生成带 GT segmentation 的 val split 标定数据集
#    ⚠ 正式生成前须与用户确认新的 --output-dir 名字；v4.2 直接复用 v4.1 生成的同名产物
uv run --locked scripts/data-generation-v4.2/generate_dataset.py \

  --episodes 0-9 --out scripts/data-generation-v4.2/outputs/color_model.npz

# 3. 留出集全帧指标 + preview（train ep10-19，160 episode，含刚性闸门）
uv run --no-sync python scripts/data-generation-v4.2/render_outputs.py \
  --h5 'artifacts/generated/v4seg-16env-20ep/record_dataset_*.h5' \
  --episodes 10-19 --out scripts/data-generation-v4.2/outputs/holdout

# 4. 两栏对比出图（预测 | GT，train ep0，16 张 + metrics.json，含刚性闸门）
uv run --no-sync python scripts/data-generation-v4.2/compare_gt.py \
  --h5 'artifacts/generated/v4seg-16env-20ep/record_dataset_*.h5' \
  --out scripts/data-generation-v4.2/outputs/compare_gt

# 5. 颜色判决分布出图（一张图 + stats.json；只读颜色表，不碰 h5）
uv run --no-sync python scripts/data-generation-v4.2/color_distribution.py

# 6. 分割过程走查出图（16 任务 × 留出集 ep10，每任务两张）
uv run --no-sync python scripts/data-generation-v4.2/segmentation_walkthrough.py

# 7. 单元测试（v4 / v4.1 / v4.2 三套一起跑，互不污染）
uv run --no-sync python -m pytest tests/lightweight/test_arm_mask_v4.py \
  tests/lightweight/test_arm_mask_v4_1.py tests/lightweight/test_color_distribution.py \
  tests/lightweight/test_arm_mask_v4_2.py tests/lightweight/test_color_distribution_v4_2.py -q
```

蓝 = 漏标的机械臂**。GT 栏的红遮罩直接涂 GT 臂像素，误差图应全白（出图链路自校验）。

## 六、实测结论（2026-08-12，全部来自 v4.2 自己重新生成的产物）

### 6.1 颜色表与 v4.1 逐位相同（拟合口径逐字未变）

重新在 val ep0–9 全帧上拟合，单进程 **1140.1 秒**，**唯一颜色 16297 种**，npz 108 KB。
与 `../data-generation-v4.1/outputs/color_model.npz` 对拍：`schema_version`、`colors`、
`counts` **三项全部逐位相等**。v4.2 只改推理侧，拟合侧一个字没动，这条对拍把它坐实。

| 列 | 语义 | 像素数 | 支撑色数 |
|---|---|---:|---:|
| 列 0 | 纯背景 | 4,731,895,750 | 12,214 |
| 列 1 | 背景∪物体混合 | 4,846,769,500 | 14,627 |
| 列 2 | 机械臂 | 342,829,732 | 1,796 |

支撑交叠：**臂 ∩ 纯背景 = 0 色**，**臂 ∩ 混合 = 126 色**，臂独有 1670 色。
「臂与纯背景零共享」是整条链路能成立的结构性前提——臂的灰白只和**物体**撞色，
不和桌面背景撞色。

### 6.2 退化引理实测核验

| 项 | 值 |
|---|---:|
| 完整流程（argmax + 否决）判臂色数 | **1670** |
| 按引理的支撑集条件（混合列没见过、臂列见过）判臂色数 | **1670** |
| 两者逐位一致 | **是** |
| 判臂颜色上的真实臂像素 | 311,704,569 |
| **判臂颜色上的真实非臂像素** | **0**（推论 1，恒等式） |
| 颜色阶段召回上界 | 0.909211 |
| 颜色阶段精确率上界 | **1.000000** |

否决代价（推论 2 的闭式，纯支撑集口径）：**126 种**臂∩混合共享色带走
**31,125,163** 个臂像素 = 全部臂像素的 **9.0789%**（`1 − 0.090789 = 0.909211`，与召回
上界严丝合缝对上）；同时这 126 色上压着 **53,143,358** 个非臂像素——这就是它们必须被
挡下的理由。

### 6.3 留出集全帧（train ep10–19，160 episode / 77,272 帧）

| 指标 | 值 |
|---|---:|
| **误标物体像素（刚性红线）** | **0** |
| 误标背景像素 | **0** |
| **标定精确率** | **1.000000** |
| 机械臂召回 | 0.818412 |
| 存在物体误标的帧占比 | **0** |
| 未见颜色占比 | 0.1866% |
| GT 兜底（setup 未覆盖 seg id）像素 | 2,278,922，其中被误标进机械臂 **0** |

逐任务召回从 **0.684357**（StopCube）到 **0.851516**（MoveCube）。
闸门输出：`刚性红线通过：留出集逐 episode 共 160 项，GT 判定的误标物体像素全部为 0`。
耗时 41.0 秒（16 进程）。

⚠ 这三个数（0 / 1.000000 / 0.818412）与 v4.1 的 veto 口径**逐位相同**——同一张表、
同一条规则，本来就该相同；相同本身就是「v4.2 只删对照口径、没动判据」的实证。

### 6.4 train ep0 两栏对比（16 张 + metrics.json）

**16/16 任务误标物体 = 0**，GT 栏自校验误标也全为 0（出图链路自身没走样）。
逐任务召回 0.719397（StopCube）～ 0.854263（VideoUnmask）。耗时 10.1 秒。

### 6.5 分割过程走查（留出集 ep10，32 张）

16 个任务全部 `该帧误标物体 0 px`；逐阶段复算与 `arm_masks_for_episode` 的运行期
逐位断言全部通过。耗时 11.7 秒。

**③ 时间平滑在 7/16 个任务的走查帧上「补」了像素**（ButtonUnmask +5、InsertPeg +4、
PatternLock +1、VideoPlaceButton +14、VideoPlaceOrder +28、VideoRepick +3、
VideoUnmaskSwap +1），其余 9 个持平或减少。这是 §3.3「③ 单独看不单调」的直接实证。
最典型的 VideoPlaceOrder ep10 第 102 帧：

| 阶段 | 像素数 | 增量 |
|---|---:|---:|
| 候选：判臂像素 | 16,636 | — |
| ① 开运算 | 16,621 | −15 |
| ② 触顶连通域 | 16,621 | ±0 |
| ③ 时间平滑 | **16,649** | **+28** ← 多数表决在补像素 |
| ④ 保守收缩 + 腐蚀 | **16,003** | −646 |

④ 的白名单交把 ③ 补进来的那 28 个像素连同边缘一起收掉，最终 mask 仍是候选的子集。

## 七、已知代价（诚实清单）

1. **臂与混合共享的颜色被否决全部带走**：灰白臂壳与灰白任务物体同色的部分照旧漏标。
   这是刚性原则的直接价钱，且由推论 2 可精确写出闭式，不是模糊的「大概损失一些」。
2. **物体误标在评估集上没有理论零保证**：拟合集上是恒等式（推论 1），评估集上依赖
   「拟合集的颜色支撑覆盖得够全」。所以才有硬闸门——数字以每次实测为准，不以推理为准。
3. **未见颜色一律不标**：标定集（val ep0-9）没见过的颜色在评估集出现时按「不是机械臂」
   处理。方向与宗旨一致（宁可漏标）。
4. **触顶规则漏掉非从上方入画的臂**（沿用 v4 口径，属可接受漏标）。
5. **③ 时间平滑单独看不单调**：整条链的单调性靠 ④ 的白名单兜住（6.5 节实测 7/16 个
   走查帧上 ③ 在补像素）。改动 ④ 时务必记得这点。
